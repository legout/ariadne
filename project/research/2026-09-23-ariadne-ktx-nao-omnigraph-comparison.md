# Ariadne compared with ktx, nao, and OmniGraph

**Date:** 2026-09-23. **Classification:** research evidence (planning-contract v1; installed provenance unknown), not an approved feature specification. **Source snapshots:** Ariadne `d3e8fd1` plus uncommitted, owner-approved local-runtime documents; ktx `49a4ae6f5b28`, nao `b5b97c582a47`, OmniGraph `e588815a452e`. The external sources below are first-party repositories at these revisions. Claims about shipped Ariadne behavior come from source; the local-runtime change is approved and planned, **not implemented**. The repositories' documentation describes intended behavior; no cross-project benchmarking or deployment test was performed.

**Current follow-up (2026-10-13):** [nao Context Builder in depth](2026-10-13-nao-context-builder-vs-ariadne.md) compares a fresh pinned nao snapshot with Ariadne after the usability work. It records runtime-versus-skill distinctions, refresh/cleanup limitations and new reuse candidates. This September note remains historical; its recorded agent-trace recommendation below has been superseded by the owner's retirement of that test tier.

## Executive finding

Ariadne and ktx are the closest competitors on *agent-consumable business context plus executable metrics*. ktx goes further in reviewed join-graph planning, multi-fact aggregation, retrieval, and incremental ingestion, but its per-connection semantic-layer format is its own YAML and its cross-database joins are currently raw-SQL-only. Ariadne instead centers OSI YAML, OKF Markdown, attached policy bodies, deterministic validation, an explicit staging/promotion boundary, and a lightweight DuckDB package. nao is a wider end-user analytics-agent product (chat, charts, feedback, evaluation, sync), with optional dbt MetricFlow-governed queries; OmniGraph is a versioned graph/context and agent-coordination **infrastructure**, not a semantic metric compiler. ### Ariadne's actual boundary

`Facade` currently owns five async methods and returns `governed:true` with compiled SQL and attached context for promoted metrics; `define_metric` passes a join-grain check, compiles and binds, runs read-only, marks `governed:false`, then stages an OSI proposal and OKF draft. `search_context` scans Markdown by word-frequency and labels staged hits as drafts. The shared source registry mounts heterogeneous sources into DuckDB; authoring profiles sources and retries deterministic validation up to three rounds; promotion merges artifacts with human confirmation and adds verification/index/log metadata. Tests include independently computed golden values, ad-hoc round-trip and fan-out traps; they are **not** a general live-agent benchmark. Crucially, compilation is not the same as proving an arbitrary agent-authored SQL fragment harmless: the MVP explicitly defers expression-injection hardening and auth/RLS, and accepts a read-only, single-statement ad-hoc trust boundary. [A-serve], [A-grain], [A-sources], [A-author], [A-promote], [A-evals], [A-mvp]

The approved 2026-09-23 spec/ADR/plan will extract `AriadneRuntime`, add a full-parity local JSON CLI, make MCP an optional extra, and teach the skill local-first usage. At the inspected source revision, `runtime.py`/`cli.py` and the `ariadne` entry point do not exist, MCP remains a base dependency, and README/skill still teach MCP-first. Do not count the planned CLI or optional-MCP packaging as current advantages. [A-runtime], [A-plan], [A-pkg], [A-skill]

### ktx: the nearest functional comparison

ktx's semantic query describes measures, dimensions, filters, segments, ordering and limits; the planner resolves a typed join graph, selects paths and handles chasm/fan traps with per-source CTE aggregation. Its wiki links pages to each other and to semantic sources; FTS5, embeddings and token search are fused with RRF. Its own docs say the compiler does not read wiki at compile time: the agent must consult it, whereas Ariadne attaches cited policies to the governed result when the served metric page resolves. Ingest reconciles evidence and accepted state, records decisions, and expects analyst review of YAML/wiki diffs. The per-connection compiler does **not** yet plan joins across federation members; DuckDB federation is exposed as read-only raw SQL. Its per-connection `semantic-layer-only` mode disables raw SQL and undeclared aggregate expressions. These are material strengths/limits relative to Ariadne's simple OSI model and its explicit governed-vs-proposal boundary. [K-sem], [K-wiki], [K-review], [K-fed], [K-config]

### nao: a larger product boundary

nao owns the natural-language user experience, charts, feedback, model testing and deployment; its CLI syncs data/repositories/Notion into context files. When configured, the semantic query tool compiles via a separate MetricFlow service, then uses the SQL executor; the backend has `prioritized` and `exclusive` semantic modes. Its `nao test` runs prompt/expected-SQL cases, compares outputs and offers a test-results UI. That evaluates the whole agent, unlike Ariadne's mostly deterministic compiler/number golden tests; nao records per-test tool calls, tokens, cost and duration, but `nao test` requires its chat server, which Ariadne need not adopt. Its context-fix collector refuses edits to generated warehouse files (they would be overwritten by sync), proposing changes to human-owned files or manual upstream fixes instead. Its root license explicitly excludes enterprise-marked files from Apache-2.0, so reusing code needs per-file license review. [N-readme], [N-cli], [N-sem], [N-test], [N-eval], [N-fix], [N-license]

### OmniGraph: adjacent substrate, not a metric alternative

OmniGraph versions typed graph facts and sources on branches, supports graph/full-text/vector hybrid retrieval and an applied configuration with Cedar enforcement and actor records. Its cluster validate/plan/apply and branch-merge patterns can inform *how to review evolving context*: destructive graph deletion requires approval of the exact plan and re-blocks on drift, while ordinary branch merge is policy-authorized but **not necessarily human-reviewed**. Adding a Lance graph server to Ariadne would not replace OSI compilation, metric grain checks, DuckDB source access or the human promotion gate. Its documented Python SDK is forthcoming; the current local embedded mode is for experiments while cluster/server deployment is its operational center. [O-readme], [O-search], [O-cluster], [O-branch]

## Recommendations for Ariadne (proposals, not authorization)

1. **First, finish the already-approved local runtime plan; do not create a competing CLI/adapter.** This is the directly relevant ergonomic idea seen in ktx and OmniGraph, but Ariadne already has a contract and tasks. Preserve one behavioral runtime for CLI and optional MCP. [A-runtime], [A-plan], [K-readme], [O-readme]
2. **Highest-value subsequent feature: answer-trace evaluation inspired by nao.** Keep `tests/evals/golden.json` as the numeric oracle; add a *small* fixture of natural-language questions run through the installed skill/actual agent and check tool choice (`get_metric` first, `define_metric` only when unmodeled), caveat citation, `governed` label and expected value. This tests a real gap (agent routing) without importing nao's chat UI, evaluator service or flaky LLM-as-judge. Begin with one deterministic recorded/tool-call check; expand to live-provider eval only if regressions warrant it. Requires its own approved behavioral source before implementation. [A-evals], [A-skill], [A-runtime], [N-readme], [N-cli], [N-test]
3. **Useful context upgrade from ktx: reconcile new evidence against approved artifacts, with traceable source-to-page links.** Ariadne authoring currently generates staged files from profile + notes, and ingestion stages typed pages; test on re-ingestion of a human-edited policy before changing anything. Prefer a bounded comparison/flag (unchanged, changed, contradiction), distinguish human-owned from generated context as nao does, and keep source citations in the existing OKF `sources[]`; not an autonomous overwrite or a second graph store. Leave the human promotion gate intact. [A-author], [A-ingest], [A-promote], [K-review], [K-wiki], [N-fix]
4. **Improve retrieval only if a small evaluation shows term-frequency search misses the right policy.** First try better tokenization/indexing or SQLite FTS5 on existing Markdown, and validate recall on real policy questions; consider embeddings/RRF (ktx/OmniGraph) only if lexical recall remains inadequate. The governed answer already structurally attaches cited policies; a vector database is not needed to make that invariant true. [A-serve], [K-wiki], [O-search]
5. **Consider ktx's multi-fact, grain-aware compilation only for observed demand.** Ariadne's current fail-closed guard can reject a safe multi-grain question; ktx pre-aggregates each fact before joining. A compatible OSI representation, join/cardinality semantics, cross-source query shape, and a fan/chasm golden proof would have to be designed and approved first. Never weaken the guard just to accept joins. [A-grain], [A-render], [A-context], [K-sem], [K-fed]
6. **Borrow a narrow provenance/approval idea from OmniGraph if context changes become multi-author.** A diff/impact preview of exactly which metric pages/policies/proposals change and which metrics cite them is more proportionate than graph branches, Cedar policy, a server or object-storage runtime. Existing staging/promotion/git already supply the MVP approval boundary. If promotion later becomes asynchronous or multi-author, bind approval to a digest of the exact proposed artifact set, as OmniGraph does for destructive plans; there is no need for this ceremony in the present interactive local gate. [A-promote], [A-context], [O-cluster], [O-readme]
7. **Do not copy the product shells.** nao's chat, charts, auth and feedback service would turn an agent-facing component into a BI app; OmniGraph's Rust/Lance fleet coordination duplicates infrastructure Ariadne does not need. Likewise do not adopt ktx's raw federated SQL as a governed metric path or silently replace OSI/OKF with its YAML/wiki dialect. Pair with these systems as consumers/storage if a concrete use case emerges. [A-context], [A-runtime], [K-fed], [N-readme], [O-readme]

**Scope caveat:** This is a source/documentation comparison, not a claim that every described feature passes independently reproduced tests. No throughput, correctness, connector-liveness, or security penetration benchmarking was run. Any recommendation changes product behavior only after the normal shaping/spec/approval route; research acceptance alone is not execution authority.
