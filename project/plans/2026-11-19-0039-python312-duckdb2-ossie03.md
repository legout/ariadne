# Plan 0039: Python ≥3.12, DuckDB ≥2.0 and Ossie 0.3

Status: **owner-approved, revision 1**, 2026-11-19 ("ja  freigabe"; supervised execution
authorized as one candidate, the plan default). Source:
[spec 0039](../specs/2026-11-19-0039-python312-duckdb2-ossie03.md) (approved),
which is sub-spec A of the [approved umbrella 0037 r2](../specs/2026-11-18-0037-simple-ariadne.md).
Target integration and publication are not authorized by this document.

## Execution model

- **Mode and host:** supervised, light. The host is herdr-core: the parent is `t1m`,
  and children are launched with `hc run` through `zsh -lic`.
- **Roles:** worker `claude-code/claude-sonnet-5-5:high`; reviewer
  `openai-codex/gpt-6.2-sol:high` (owner choice, 2026-11-19).
- **Writers and worktrees:** one sequential writer in an isolated worktree under
  `~/.local/state/worktrees/`. The base is `origin/main` at dispatch. The owner's
  uncommitted ruff-format edits in the main checkout are not carried over.
- **Commits:** one commit per task, or more where a task says so. Each test-touching
  task runs its focused checks. The full CI-equivalent run happens once, at V.
- **Review:** an independent review of the T3 to T5 contract and compiler changes
  (high risk). One fix pass, then one delta recheck.

## Tasks

### T1 — Python ≥3.12 and ruff `py312` (`existing-check`)

Sources: spec §3; AC1.

- Set `requires-python = ">=3.12"` in the four packages and every ruff
  `target-version` to `py312`.
- Fix all syntax that does not parse under 3.12. Today these are the
  unparenthesized `except` clauses.
- Refresh `uv.lock`.
- Add the CI matrix: full on 3.12 and 3.14, smoke on 3.13. The Docker image stays on
  3.14.
- Check: `python3.12 -c ast.parse` over every source file; wheel build and install,
  then the Core walkthrough on 3.12.

### T2 — DuckDB 2 (`existing-check`, plus a probe)

Sources: spec §4; AC2.

- Change the dependency to `duckdb>=2.0,<3` and refresh the lock.
- Port the removed relation `fetchone`/`fetchmany` calls in `execution.py`,
  `contract_inspection.py`, `sources.py`, `sql_authority.py` and `validate.py`.
  Check `lumio-workspace` too: `state.py` uses sqlite3, not DuckDB.
- Check: the existing focused bounded-result, deadline and source-type tests.
- Re-run the lock_down probe under 2.x as throwaway code in `/tmp`. Append the result
  to `project/research/2026-11-19-lockdown-spike.md`.

### T3 — Ossie loader and schema (`new-test` for the refusal paths)

Sources: spec §5.1, §5.2; AC3 (loader part) and AC6.

- Vendor the pinned `ossie-schema.json`, with its license note, into the package
  data.
- Change the single loader used by `validate`, `semantic_graph`, `query`, `discovery`,
  `context`, `contract_inspection`, `status`, `authoring` and `lumio_context` to read
  root documents.
- Refuse `semantic_model:` with a pointer to `ariadne migrate`.
- Validate `ARIADNE` extensions and preserve other vendors' entries.
- Update the `graph.yml` keys (`from`/`to`, plus `cardinality` only for one-to-one).
- One test per refusal class in the existing `test_validate.py`/`test_multifact.py`:
  - legacy envelope;
  - schema violation;
  - unknown `ARIADNE` key;
  - foreign vendor preserved.

### T4 — Name resolution and compiler (`new-test` + `existing-check`)

Sources: spec §5.3, §5.4; AC4 and AC5.

- `render.py`/`planner.py`/`grain.py`/`semantic_graph.py`:
  - fields resolve from source columns;
  - keys and relationship columns are fields;
  - `source.column`;
  - dataset-scoped metrics as fact-branch measures;
  - `AGG(dataset.metric)` derived metrics;
  - refusals for field→field, metric→metric and multi-dataset raw aggregates;
  - `expression.sql` is authoritative.
- New tests: the AC4 cases and the AC5 arithmetic goldens. Each expected value is
  hand-worked.
- The existing compiler, multi-fact and grain tests must pass after T6 migrates their
  fixtures. Until then they run against fixtures converted by the T6 converter. T4 and
  T6 may therefore interleave: write the converter first, then use it to update the
  fixtures.

### T5 — Metric identities (`existing-check` + `new-test` for ambiguity)

Sources: spec §6; AC7.

- Identity construction and parsing, wherever metrics are named (query, Policy
  Binding validation, `lumio_context` metric index, discovery/status, Answer Examples,
  Computation pages).
- Short-name resolution with refusal when ambiguous.
- Confirm that the Lumio `metric_ref` validation accepts dotted metrics; if not, make
  the minimal SDK change and report it.
- Tests: ambiguity refusal; admission with the new identities; required-Context refusal
  before SQL still holds.

### T6 — `ariadne migrate` and the repository migration (`new-test`)

Sources: spec §7; AC8, AC3 and AC9.

- Implement the converter as a CLI subcommand of `ariadne` (the existing `cli.py`)
  that writes through the Authoring Proposal route.
- Unconvertible constructs produce a per-file report and leave the project unchanged.
  Re-running is idempotent.
- Run it over all tracked fixtures, examples and in-code envelopes. This covers the
  ~22 test modules plus `tests/fixtures`, `integration/examples` and
  `setup_wheel_walkthrough.py`.
- Tests:
  - migrate the integration example → admit → `revenue` = 150 and
    `completed_orders` = 2;
  - second run is a no-op;
  - an unconvertible project is left unchanged, with a report.
