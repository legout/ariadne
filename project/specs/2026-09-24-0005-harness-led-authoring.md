## Scoped HTTP extension — owner-approved 2026-10-10

The owner requested Compose-compatible HTTP binding and health/readiness only,
then selected bearer protection for both probes and active-toolset readiness.
This bounded extension authorizes implementation/tests/documentation, not
publication or deployment. Loopback remains default; explicit
`--http-container --http-host 0.0.0.0` permits a private container-network bind
without publishing the Ariadne host port. Private external HTTPS and all source,
project and human-admission boundaries remain binding. Host/Origin identities
are explicitly configurable while SDK DNS-rebinding protection stays enabled.

Acceptance: `/healthz` returns a minimal 200 liveness status; `/readyz` returns
200 for Authoring without requiring a catalog, while Analyst/Combined require
usable metric discovery through the shared QueryRuntime (including admission
checks). Failures return neutral 503 without exception/project details. Both
GET/HEAD routes require the existing bearer token, including on container binds.
No metric calculation is used as a probe; lazy runtime setup may perform the
existing bounded initialization of approved sources. Readiness does not attest
all graph operations, current source connectivity or numerical correctness.
Stdio and the MCP tool inventory remain unchanged. Default non-loopback refusal,
container auth, allowed/rejected Host/Origin, not-ready query projects and a
ready catalog receive focused checks (`new-test`); existing MCP journeys cover
parity (`existing-check`). No new domain term or architectural decision is
introduced; planning-contract v1, installed provenance unknown.

## Purpose and scope

A user supplies dataset locations and domain evidence; an agent harness uses **its own model** to propose the source registry, Seed Notes, Semantic Layer (OSI), and Context Layer (OKF). Ariadne measures the data, converts documents, checks proposals, and holds them for human review. The harness may ask the owner questions where the evidence does not establish a business rule. Neither source access nor Promotion may be inferred from an agent assertion.

The same authoring behavior is available through a packaged skill invoking local commands, local stdio MCP, and authenticated private-network HTTP MCP. A remote server owns one configured project; clients do not choose filesystem roots. The existing `ariadne-author` OpenAI-compatible authoring mode and the five query/ad-hoc operations remain available. The local workflow does not require MCP, an HTTP service, or a second LLM credential.

This specification makes an **additive exception** to the five-tool and no-HTTP-service scope of the approved [local-runtime specification](2026-09-23-0001-local-artifact-runtime.md): new authoring operations and an opt-in HTTP transport, without changing the five existing query contracts. It also widens ADR-0009's standalone-document boundary **only for explicitly initiated harness-led authoring**, and revises ADR-0007's computation-attester rule for a metric without an independent oracle: its computation must explicitly mark independent attestation pending instead of citing the demo test harness. Ordinary `ariadne-ingest` and opt-in Policy reconciliation retain their existing contracts. The affected sources are reconciled by scoped cross-references to this approved revision; their earlier behavior remains authoritative outside this new workflow.

Non-goals: an agent-driven Promotion tool, executing unvalidated metric SQL, unrestricted remote file browsing, arbitrary project selection, uploading large datasets over MCP, using the server's model to impersonate the harness model, auto-accepting business rules, changing existing OKF/OSI formats, or making the local CLI depend on MCP.

## Evidence and source-access boundary

1. **Sources.** The harness may propose registry entries (local paths, approved server-readable mounts, or supported object-store URIs such as S3 Delta/Parquet). Proposals are data, not active connections. Ariadne checks their shape and displays the precise locations; only a human-operated server-side approval command may install them in the project's `ariadne.yaml`. No profiling or query opens a newly proposed location before that approval. Server-side DuckDB credentials stay in server configuration; registry proposals must not contain inline credentials. A remote client's local dataset path is *not* a server path: the operator first stages/mounts the data on the server or makes it available in object storage. Locally, paths resolve under the existing registry rules. A source change while a bundle proposal is active invalidates that proposal until re-profiled and revalidated.
2. **Documents.** The harness may reference server-readable documents (including configured object-store references) or submit a bounded document upload through authenticated MCP. Local skills can supply local paths without upload. The operator configures the **exact approved object-store document URIs** and the **allowed local input roots** in the human-managed project config (`ariadne.yaml`, `documents:` section with `object_store:` and `roots:`) — never in server environment variables or client request arguments. A client-supplied reference may only name an already-configured URI or a path inside a configured root; anything else is rejected before any network or file access. Approved object retrieval uses server-held credentials (S3 references are the specified minimum object-store case; no HTTPS credential-in-URL scheme is introduced), retains the original bytes and digest in the project-controlled input area, and converts them through the existing optional document converters: native Markdown/text, PDF, and supported office/HTML formats. Unsupported formats, missing converters, unreadable references, and over-limit uploads fail explicitly without silently dropping evidence. Large documents use pre-staging or an object-store reference, not unbounded MCP payloads. A client-supplied path never grants access outside operator-configured input roots or approved references.
3. **Inputs for the harness.** After source approval, the server returns the existing deterministic per-source profile, converted document text with source identity and digest, and an optional existing approved Seed Notes file. Responses are bounded and can be fetched in parts, with no omitted content represented as complete. The operator has explicitly allowed the authenticated harness to receive the full profile (including low-cardinality top values), converted document content, and Seed Notes. Source credentials are never returned. Sending an already approved Policy body to a model for reconciliation remains separately opt-in under ADR-0009.
4. **Limits of inference.** The profile is measured by Ariadne, not authored by the model. The harness can propose explanations and rules from documents or owner statements, but must mark unsupported or contradictory claims for review rather than treating data distributions as business-policy evidence. Source citations identify the actual input and digest; page numbers or quotations are reported only when verified against extracted evidence. Semantic truth is not established by compile success.

## Authoring interface and lifecycle

One transport-neutral authoring service owns the source-proposal, input-preparation, submission, and review operations. The local command surface exposes these as `ariadne-authoring propose-sources --file FILE`, `ariadne-authoring inputs`, `ariadne-authoring submit --file FILE [--base-digest DIGEST]`, and `ariadne-authoring review`. A human-only `ariadne-authoring approve-sources --digest DIGEST` runs on the server host; the packaged skill must never invoke it as the agent. `ariadne-promote` remains a distinct human operation. The MCP adapter exposes corresponding source-proposal, inputs, document-upload, bundle-submission, and staged-review tools, **not** source approval or Promotion tools. Stdio and HTTP MCP use the same service and response contracts as the local commands. HTTP is opt-in and bound to one server-configured project: it listens only behind private-network HTTPS and requires a server-configured bearer token on every request, including reads and uploads; missing or invalid tokens fail before any project data or tool action is available. The token is supplied via a server environment variable, never through `ariadne.yaml`, tool responses, or logs; local stdio and CLI do not require this token. No client argument selects a filesystem root or source credentials.

A submitted bundle carries complete proposed Seed Notes (`data/seed_notes.md`), OSI models, and OKF pages as relative paths and contents. The server accepts only these documented artifact roots, refuses path escapes, symlinked staging components, generated `index.md`/`log.md`, and unbounded submissions, and does not write directly to served layers. It reuses the existing authoring checks: compile and bind, the grain audit, bundle presence and per-type frontmatter, metric enrichment and computation generation, lifecycle stamping, and the `review_needed` rule. The same checks apply to local and MCP submissions. Validation errors identify affected files/requirements and permit the harness to repair the **same** proposal; they are not approval. Generated provenance must name harness-led authoring, not falsely identify the server's OpenAI-compatible model. For new metrics without an independent expected-value check, computation pages carry an explicit `attestation: pending` state instead of an invented `attester` such as `tests/test_evals.py`; the per-type contract accepts this honest state. A real attester, if supplied and verified, can be cited instead. Compile and grain checks are named separately from independent value attestation; `verified` at human Promotion records review, not a numerical oracle. The established three-round authoring limit applies per proposal; exhausted failures remain `review_needed` for human resolution.

Only one active full-bundle proposal exists per configured project. Its digest/revision is returned on every submission; repairs require the current digest and stale or competing submissions fail without replacing files. The active state survives a server restart; no unrelated ad-hoc or standalone-ingest proposal is silently overwritten. Re-submitting identical content does not create another candidate or reset the attempt count. A proposal that cannot be safely resumed is reported for human resolution rather than reset by the agent. After an interrupted transition — when the staged bundle, a retained prior copy, and the persisted state disagree, or a prior copy is left behind at all — every agent retry, replacement, review, and Promotion is refused: both copies and the state are preserved untouched for human comparison and resolution, with no auto-restore, no silent reset, and no agent or single-command shortcut that deletes evidence. The superseded prior copy is dropped only inside the same locked transition that durably stored its replacement; a cleanup failure reports the retained copy instead of hiding it.

`review` returns an inventory, source identities, converted-document citations, the proposed Seed Notes and artifact bodies (retrievable in bounded parts), validation state, and an exact content digest. This is readable through local commands or MCP, but never counts as a human sign-off. Approved `ariadne.yaml` is a separate earlier access decision; proposed Seed Notes remain unverified until the final human review. Human Promotion on the server takes the reviewed digest, refuses a changed, incomplete, or `review_needed` proposal, and applies the reviewed Seed Notes plus OSI/OKF through the existing merge-only Promotion and verification bookkeeping. No MCP authoring call can invoke Promotion; the human command must name the project's staging and served roots explicitly. The operator resolves conflicts or declines the proposal without an agent clearing the gate.

Authoring and input preparation work in an empty project, before any metric is served. The current query runtime's requirement for promoted models cannot block startup of the authoring tools. Existing query calls retain their present error when no promoted models exist; once promoted, they see only served state. A server restart does not turn a staged proposal into a governed metric.

## Failures, compatibility, and acceptance

Input conversion or profiling failure returns the specific blocked source or document. Missing authorization, invalid registry entries, unsupported formats, oversized uploads, path escapes, stale proposal digests, and simultaneous writers fail before they change the active proposal or served state. A failed validation reports errors without claiming a metric is correct; a model failure is the harness's concern, not a reason for the server to switch to its own model. Existing `ariadne-author`, `ariadne-ingest`, `ariadne-promote`, and the five query interfaces keep their default behavior.

Acceptance examples:

1. In a fresh local project, a skill-driven harness proposes a local Parquet or Delta source; before operator source approval no profiling opens it. After approval it receives a real profile plus a local PDF's converted text, proposes Seed Notes and OSI/OKF, repairs a grain failure, and leaves one reviewable, not-yet-served bundle. No OpenAI-compatible endpoint is required.
2. A remote harness connects to the private HTTPS MCP server with the configured bearer token, proposes an S3 Parquet/Delta source and uploads a supported small domain document. A missing or incorrect token discloses no project data or tool access. The source cannot be read before a human approves its entry. After approval the server profiles using server-held credentials, returns source-linked converted text, and stages the harness's validated proposal on the **server**, not on the client. The same operations work through local stdio MCP before first Promotion.
3. When documents and statistics do not define a revenue-exclusion rule, the harness asks the owner or flags the uncertainty; a plausible rule invented from profile distributions is not presented as established. A human reviews the proposed Seed Notes and cited policies along with the models. Compile success never serves or verifies them.
4. A second writer, a stale revision, a changed source registry, and an identical retry cannot replace or multiply the active proposal. Failure after three rounds remains `review_needed`. A restarted server preserves the active review state.
5. A human remotely reviews proposal bodies and digest through MCP; a later human-operated server-side Promotion with a mismatched digest or `review_needed` status fails without serving anything. With the matching digest, the proposed Seed Notes and artifacts are accepted together, and the existing verified/index/log bookkeeping applies. An untested new metric's computation remains clearly marked `attestation: pending` even after human review; it never cites the demo evals as its attester. A governed query must carry this caveat: `governed: true` means Promoted, not independently value-attested. No MCP tool can do this step.
6. The existing local OpenAI-compatible `ariadne-author`, standalone `ariadne-ingest`, and five MCP/query operations pass their current acceptance tests unchanged; the local skill/CLI route works with the MCP extra absent.

## Capture checkpoint and outstanding verification

- **Vocabulary:** `CONTEXT.md` now defines Seed Notes as human-owned business-rule input that may be harness-drafted but is authoritative only after human approval, and distinguishes a pending Computation from an independently Attested Computation. Existing Staging, Promotion, Bundle, and Authoring Agent terms otherwise apply.
- **Decisions:** accepted ADR-0013 explains harness-model ownership, server-owned measurements and checks, source approval plus final human Promotion, and honest independent-attestation status, including the remote disclosure boundary. ADR-0007, ADR-0009, and the local-runtime specification contain scoped references to this revision; ADR-0003's human-only gate remains intact.
- **Behavior:** this approved revision owns the new local/MCP workflow; its approval alone authorizes neither implementation nor publication.
- **Prerequisite evidence:** the installed MCP SDK 1.30.0 exposes `streamable-http` (verified in this session); planning must verify the selected private-network HTTPS deployment, server-side bearer-token enforcement, and converter behavior for remote document references before promising a running endpoint. If an option is unavailable, return to design approval rather than silently selecting another transport.
