# Dosi and Datus Agent compared with Ariadne

**Date:** 2026-09-29. **Classification:** research evidence, not a new specification or permission to change runtime behavior (planning-contract v1; installed revision unknown). **Snapshots:** Datus-agent [`6545a0d72470`](https://github.com/Datus-ai/Datus-agent/tree/6545a0d7247028377d0c2601581f101f75f9b20f) (`pyproject.toml`: 0.4.2), dosi-dist [`cb75c89`](https://github.com/Datus-ai/dosi-dist/tree/cb75c89), Dosi wheel `dosi-engine==0.1.12`; Ariadne `edc7428` plus **uncommitted working-tree changes**, explicitly including its context vocabulary and authoring files. The Dosi website and versioned Datus docs were read on this date; Dosi's Rust source is not public. The small executable probes below used disposable directories and did not change Ariadne's repository. This is not legal advice or an independent vendor performance audit.

**Publication note (2026-09-30):** The original comparison is a dated snapshot. Answer Examples have since been implemented under ADR-0015 and specification/plan 2026-09-29-0007. The Trace Data example and vendor comparison clones described below are local-only, not included in this repository; their live counts are observations, not reproducible golden values from a GitHub checkout.

## Executive decision

**Do not replace Ariadne's compiler or add LanceDB now.** The license has materially improved, but Dosi is still **ELv2 binary-only, not Apache/MIT open source**. Its genuinely impressive **branch-local, grain-aware multi-fact SQL planner** solves a problem our single-dataset renderer deliberately does not; it earns a controlled evaluation if Ariadne must answer such questions, not a speculative replacement today. The *simpler* ideas to borrow are discover → compile/preview → execute with structured repair hints and bounded outputs, and using evaluated, source-linked examples to distill missing business rules. Some are already approved or shipped in Ariadne; finish those paths rather than introducing Datus Agent's whole stack. [D-license] [D-semantics] [A-adr8] [A-context-spec] [A-examples]

| Candidate | Real advantage | Ariadne fit / decision |
| --- | --- | --- |
| Dosi as metric compiler | Multi-dataset branches, cross-fact rollup, conformed dimensions, native multi-dialect SQL, windows/parameterized metrics, attribution | **Investigate when required**, with a model-and-result parity gate; not a drop-in for an embedded SELECT or our runtime/gates. ELv2 binary distribution and format migration are material costs. |
| Dosi's agent-facing error/catalog contract | Candidate names, recommended dimensions, typed errors, compile/explain before executing, result caps | **Borrow selectively** in existing `AriadneRuntime`/CLI/MCP when an observed agent trace fails; no new server/SDK. |
| Datus Agent's context split | Trees for navigation; semantic search for schema/metric/SQL; explicit atomic facts, short agent memory, project inventory | **Borrow classification and tested retrieval ideas**, not its mutable KB or automatic knowledge promotion. Ariadne's OKF/OSI authority split and answer-example design already express this more safely for governed numbers. |
| LanceDB | Embedded vector, hybrid, full-text and structured KB tables; per-project/datasource scoping | **No today**: it neither compiles metrics nor enforces governance. At most trial as a disposable *index of* approved OKF/example records after a measured paraphrase-recall miss. |

## 1. Separate the products, license and integration boundary

- **Dosi** is a Rust semantic runtime. It loads the older Apache Ossie/OSI `semantic_model:` YAML document, validates it, builds a plan and emits dialect SQL; CLI, Python wheel (`dosi_engine.Engine`), REST/Arrow and MCP share this engine. It is not a conversational agent, schema crawler, knowledge store or general free-form text-to-SQL tool. Its `/v1/metrics`, `list_metrics` and `lineage` are a **modeled metric catalog**, not document retrieval. The newer upstream single-model document format is not accepted by Dosi 0.1.12. [D-home] [D-semantics] [D-release] [D-rest] [D-install]
- **Datus Agent** is an Apache-2.0 Python data-engineering/chat product. The tested Git source at `6545a0d72470` declares `dosi-engine==0.1.12`, `lancedb==0.34.0`, `fastembed`, DuckDB, OpenAI Agents/LiteLLM and UI/integration packages. It combines Dosi metrics with metadata discovery, SQL generation, reference queries, skills, subagents, sessions and a knowledge base. **The published `datus-agent==0.4.2` wheel inspected during the later clone test lacks that Dosi dependency and integration**; use the pinned Git revision for this experiment. Its Apache license does **not** relicense the separate Dosi binary dependency. [G-pkg] [G-intro]
- **License change:** Dosi 0.1.9 changed the earlier proprietary grant to **Elastic License 2.0**. ELv2 explicitly allows free download, commercial production use and redistribution, but forbids offering substantial Dosi functionality to third parties as a hosted/managed service, bypassing license-key functionality and removing license notices. `dosi-dist` publishes **binaries and wheels, not source**. This lifts the former no-grant obstacle for many embedded uses; it does **not** allow calling it unrestricted/open source, and the hosted-service boundary needs owner/legal review before a distributed offering. The license of `datus-semantic-osi`/its old AGPL MetricFlow path in [the previous spike](datus-spike.md) is a **different question**; the new Dosi wheel does not inherit its AGPL simply because Datus Agent uses it. PyPI 0.1.5 misleadingly advertised Apache-2.0 metadata while the vendor's 0.1.9 release notes say its earlier grant was proprietary: rely on the actual **0.1.12 archive LICENSE**, not an old metadata field. [D-license] [D-release] [D-dist] [G-pkg] [A-spike]
- Dosi's installed Python wheel offers `Engine(model_path=...)`, `.metrics()`, `.dimensions(metric=...)`, `.compile(query, dialect='duckdb')`, `.execute()`, `.attribute()`, `.lineage()`. It exposes `SPEC_VERSION='0.2.0.dev0'`, DATUS extension version `1.9` and a renderable authoring contract; an author can read the installed schema rather than guessing extension keys. We successfully installed/imported `dosi-engine==0.1.12` in a Python 3.12 disposable uv environment on macOS arm64 and compiled every metric in two **local-only** `examples/trace-data/semantic_layer/models/*.yml` files (`latest_eol_motor.yml`, `traced_motor.yml`). This proves **parsing and compilation of these two files**, not execution parity or compatible runtime migration. Dosi's Python API reference is still incomplete. [D-install] [A-trace]

## 2. What Dosi actually buys in metric planning

The important difference is **where the aggregate is evaluated**. Dosi's [published semantics contract](https://dosi.datus.ai/semantics/#6-fan-out-protection-branch-assignment) says additive measures are evaluated at the dataset that owns them; join edges must be grain-safe (many-to-one); disjoint measures aggregate in **separate branches** and merge on group keys, with conformed dimensions/time axes where declared. It can reject ambiguous paths rather than choosing one. It also classifies aggregate/ratio/expression metrics; supports group/time grains, detail queries over modeled fields, derivation, windows, parameters and metric-change attribution. `--osi-basic` and `--osi-datus` separate upstream core from Datus extensions; some attractive behaviors require the latter and are **not** portable core-Ossie semantics. Do not infer every dialect executes every feature identically from the dialect list. [D-semantics] [D-extensions] [D-mcp] [D-release]

**Independent two-shape probe using Ariadne's existing fan-out fixture** (`tests/evals/build_trap_fixture.py`, three orders + six lines, expected order revenue NA 300 / EMEA 400):

1. Load Ariadne's **existing** `trap.yml` where `trap_join.source` is a pre-joined `orders JOIN order_lines` SELECT, then ask Dosi 0.1.12 for `orders_total` by `trap_join.region`. It **compiled**, returned `SUM(trap_join.amount)` over that SELECT, and executing on the fixture returned **NA 700 / EMEA 400**: still inflated. Its claimed fan-out guarantee cannot recover a parent grain hidden inside a single SQL-source dataset or correct a false `primary_key: [order_id]` declaration. Ariadne's `check_grain_preserving` remains necessary for this input. No production Dosi query was executed. [A-trap] [A-grain]
2. In a disposable model, represent `orders` and `lines` as **separate datasets**, declare their real keys and `lines -> orders` relationship, and ask for `SUM(orders.amount)` plus `SUM(lines.line_amount)` by `orders.region`. Dosi compiled two separate aggregate branches with a FULL OUTER JOIN and returned **(NA 300, 300), (EMEA 400, 400)**; both single-metric queries were also correct. This confirms its useful *documented model shape* on one live fixture, not universal fan-out immunity, declared-key truth, or parity across source connectors. [D-semantics] [A-trap]

**Comparison with Ariadne:** Our `render.py` handles one dataset/envelope, base aggregates and recursive derived expressions via sqlglot; `AriadneRuntime` executes compiled SQL on its long-lived DuckDB connection. `grain.py` refuses one-to-many joins in an ad-hoc or served dataset SELECT; authoring guidance recommends pre-aggregation. The prior upstream #1426 was against **`datus-semantic-osi`**, not this newly probed Dosi engine. ADR-0006's statement that *the engine* lacks branch-level protection described that previous engine and Ariadne's deliberate current renderer; it cannot be generalized to correctly modeled Dosi 0.1.12. Nonetheless Ariadne's fail-closed facade contract is still valid for its existing single-SELECT path. Do not quietly rewrite accepted ADRs/specs based on research; a different compiler/behavior needs a shaped owner decision. [A-render] [A-runtime] [A-adr6] [A-adr8]

**Other Dosi capabilities:** Built-in lineage and change attribution could become useful for a governed cross-fact query UX; currently Ariadne returns SQL, OKF metric page and cited Policy bodies, not an attribution engine. Dosi's native REST/MCP offers compiled query, `explain_query`, `run_query`, `validate_model`, discovery, structured error codes/candidates/hints, conservative row caps and compile-only mode. Ariadne already has local-first CLI and optional MCP over one runtime, read-only execution and full policy attachment; replacing them with a second `dosi-server` would duplicate the surface and lose the existing served/staged distinction. Dosi documentation claims 10–20× faster than MetricFlow and Arrow benefits, but the published benchmark uses the vendor's MetricFlow fork and its own test fixture, not Ariadne's sqlglot renderer or real Ariadne queries; **no Ariadne speedup has been established**. [D-mcp] [D-benchmark] [A-runtime] [A-adr11]

**Actual migration obligations if evaluated later:** translate/query Dosi's `MetricQuery` (qualified `group_by` fields, time semantics, filters, metric names) from Ariadne's existing interface; check each existing OSI model and Datus extensions against 0.1.12; handle in-memory ad-hoc models (Python `Engine` is file-based) without writing into served files; compile SQL and still execute on **our own DuckDB connection** with per-connection SQLite/remote mounts; retain single-statement/bind/grain gates, OKF policy attachment, staging/promotion and `governed` labels; test every golden metric and fan-out fixture including both model shapes. Dosi native execution/standalone MCP is *not* assumed to share Ariadne's DuckDB attached session. The binary-only ELv2 wheel becomes an additional platform, upgrade, audit and distribution obligation; source-available OSS semantics would be a separate proposition. [D-install] [D-mcp] [A-runtime] [A-adr8]

## 3. Datus Agent's context architecture (not Dosi's)

**What is persistent:** Datus divides (a) an `AGENTS.md` project inventory and `knowledge/*.md` for atomic business facts; (b) per-agent `.datus/memory/{node}/MEMORY.md` with a hard **2,000-byte** limit for preferences, inherited read-only by child agents; (c) semantic-model **YAML as source of truth** under `subject/semantic_models/`, with projected metric/semantic-object rows in the KB; (d) validated `reference_sql` and parameterized reference templates with summaries/search text, plus table DDL/columns/sample rows and official platform docs; and (e) a domain **subject tree** and physical **catalog tree** for navigation. It reconciles changed/deleted YAML into derived KB rows. Do not equate a searchable/generated KB row or a learned fact with an approved, governed definition. [G-context] [G-intro] [G-reconcile] [G-memory] [G-skills]

**How context reaches the agent:** `/init` quickly writes a project inventory and file knowledge without vectors. `/build-kb` proposes a generation manifest, then generates/indexes semantic models, metrics and reference SQL after confirmation. A project `AGENTS.md` first 200 lines and eligible memory are injected into the system prompt; skill catalog descriptions/required skills are supplied there too. At the question level, an agent or a human can browse `/catalog` and `/subject` or inline `@Table`, `@Metrics`, `@Sql`, `@File`. `context_search_tools` first lists the subject tree, then retrieves metric/semantic objects/reference SQL by similarity, with exact-detail retrieval separately; `ask_metrics` embeds a **bounded tree preview** and exposes full tree lookup when it grows. Subagent `scoped_context` limits searchable tables/subjects and tools; async task overrides use `ContextVar` so siblings do not leak scopes. Session/tool-output compaction is **another** concern: minor passes archive large old tool I/O; major passes summarize history. Neither session compression nor agent preference memory constitutes the domain Context Layer in Ariadne's sense. [G-context] [G-tools] [G-ask] [G-scope] [G-prompt] [G-cli]

**Routing is a real product boundary:** Datus Agent has a broad `gen_sql`/schema-linking/execute workflow for raw exploratory SQL and a separate `ask_metrics` subagent with a narrow metric-only tool set. The latter prefers a direct subject-tree match, then similarity search if ambiguous, gets the metric's accepted dimensions, calls Dosi's metric query/attribution tools, and **does not fall back to raw SQL** when no modeled metric answers. Newly generated Datus metrics become available after validation and KB synchronization without Ariadne's human Promotion step; that is a different authority policy, not a feature to import accidentally. Ariadne's packaged skill already says governed metric first, then explicitly labeled ad-hoc proposal when necessary, so an optional metric-only agent/tool allowlist is worth considering only for a consumer that must never take the ad-hoc route. [G-ask-metrics] [G-workflow] [A-skill]

**Where LanceDB fits:** The default local KB has per-project/per-datasource Lance tables for embeddings, vector search, **hybrid vector+FTS**, plain non-vector KB rows and metadata full-text indexes; SQLite stores structured/session data. PostgreSQL+pgvector is an alternative team backend. Datus's local `lance_backend.py` performs `search_vector`, `search_hybrid` with linear-combination rerank, `search_fts`, filtered reads/upserts, index maintenance and version cleanup. FastEmbed/OpenAI supply vectors (LanceDB is storage/search, not an embedding model). Since 0.4, `kb.search.mode: fts` can **replace metadata vector retrieval only**: keywords/identifiers/DDL/sample rows/semantic profiles are indexed; metrics/reference SQL/docs keep their own modes. A mode switch requires an overwrite bootstrap, incremental updates need a healthy existing index, and an incompatible index errors rather than silently falling back. This is a meaningful ops cost, not a free recall improvement. [G-intro] [G-lance] [G-kb] [G-fts] [G-pkg]

**What maps to Ariadne:** Ariadne has a canonical OKF Context Layer (Policies/caveats) separate from OSI calculations; `search_context` scans served and visibly draft Markdown, returns full pages plus passage/path/line pointers, and `get_metric` structurally attaches the promoted metric page and cited Policy bodies even if retrieval misses. Its *approved* context-retrieval spec explicitly excludes embeddings/vector stores and only permits FTS5 after the recorded top-five cases fail the current lexical path. The small checked-in retrieval evaluation has five questions; the local-only trace-data served example had 22 Markdown pages at inspection. The Answer Example spec/ADR was approved but not yet implemented at the original inspection; issues #19–#21 have since implemented its explicit reviewed per-project OKF store, fresh-query validation and dependency staleness. Datus's automatically learned rule/SQL example must **not** bypass human source/Promotion gates or mix a historical answer into a governing Policy. [A-context-spec] [A-runtime] [A-context-eval] [A-examples] [A-adr15]

## 4. Skills: patterns worth copying, not files to vendor

Datus Agent ships `init`, `build-kb`, `storage-classify`, `extract-knowledge`, `memory-organization`, `session-summarize`, `dosi-semantic-authoring`, validation/migration and BI integration skills. They bind to its own `task`, SQL, memory and KB tools; pasting their SKILL.md files into Ariadne would teach unavailable tools and different authority. The docs say `extract-knowledge` can be triggered after a successful query, while the checked-in skill explicitly asks for a `(question, gold_sql)` pair and permits user invocation: **do not assume every successful Datus chat silently validates or saves a fact**. [G-skills] [G-extract] [G-classify] [G-dosi-skill]

1. **High-value experiment — blind knowledge-gap extraction from independently checked question/answer pairs.** Its *deep* path keeps a SQL-generating subagent blind to the gold SQL, compares results, and distills only non-inferable, atomic business rules (status code, required filter, join trap, strict date boundary). This addresses Ariadne's real challenge of extracting domain meaning from validated evidence; it is not proof that a chosen SQL or a model's own answer is gold. Use the approved Answer Example flow for explicit historical references; any proposed Policy goes to `staging/` with verified citations and human Promotion. No automatic write after a mere successful query. Adapt only after a real trace shows missed rules. [G-extract] [A-examples] [A-adr15]
2. **Already mostly present — classify artifacts before storing them.** Datus separates declarative business facts, metric definitions, historical executable examples, tiny personal preference memory, project navigation and procedures. Ariadne already separates OKF Policies, OSI metrics, Seed Notes, Answer Examples (approved design), packaged skill and research; add no generic `storage-classify` router unless agents demonstrably misfile examples as policies. Datus's good narrow detail is to keep the *original user question* as searchable text alongside a checked query, rather than only indexing SQL tokens; the approved Answer Example fields already retain it. [G-classify] [A-examples] [A-context]
3. **Useful discipline — bounded manifest before expensive generation; source-aware model authoring.** `/build-kb` asks approval of a scoped generation manifest; `dosi-semantic-authoring` disallows invented primary keys from sample/statistical hints and reads the installed Dosi extension contract. Ariadne already has operator source approval, deterministic profiling, digest-checked staged submission and human Promotion; do not weaken these. Datus's strict DDL-only key rule trades coverage for certainty: Ariadne's observed profiler/cardinality evidence and validation have their own approved contract, so don't blindly transplant it. [G-build] [G-dosi-skill] [A-skill]
4. **Low priority:** memory-organization/session-summarize target a persistent conversational agent and need human confirmation; Ariadne is primarily an agent-facing metric component with its own external host agent. BI publishing, migration and scheduler skills have no current Ariadne job. Do not add a Datus-style conversation memory store, background self-learning loop or huge prompt framework. [G-skills] [A-context]

## 5. Decision gates and suggested smallest next step

**Now:** keep current dependencies and the approved retrieval and Answer Example execution order. If an actual agent trace reveals unhelpful errors or dimension choice, improve **one** error/catalog field inside the existing runtime and evaluate on that trace; no engine swap. If the lexical corpus starts missing policy paraphrases, add **measured cases first**, test the already-authorized FTS5 gate, and only consider vectors/Lance in a newly approved scope if lexical retrieval demonstrably cannot meet recall without unacceptable trade-offs. A vector hit is a *pointer* to a source page, never authority for a number. [A-context-spec] [A-context-eval] [A-runtime]

**When to reopen Dosi:** a concrete need for a parent+child fact total in one governed request, conformed cross-fact dimensions, non-DuckDB SQL, or advanced windows/attribution that cannot be expressed simply as today's safe model. Compare on a small, independent workload: golden values (including null keys and unpaired groups), Ariadne `trap.yml` **and** separate-dataset model, compiler error behavior, Python wheel/platform fit, per-connection attaches, ad-hoc gate and distribution/legal policy. Only after parity and operational/legal approval should an owner consider superseding ADR-0008/0006 and approving a new spec/plan. The probed branch planner is a reason to *evaluate* Dosi, not a license or correctness waiver. [D-semantics] [D-license] [A-adr8] [A-adr6]

**If LanceDB is ever evaluated:** first measure a representative paraphrase corpus over real, reviewed OKF/answer-example files with offline/online resource budget; compare SQLite FTS5 and a disposable vector index on the **same** top-k, draft marking, citation freshness and changed/deleted-page cases; keep source text in Git, index rebuildable/fallback to lexical, and never rank an unapproved draft as authority. Add an embedding provider, LanceDB, freshness and index lifecycle only if the measured gain justifies them. No claim of measured improvement for Ariadne's current tiny corpus is made here. [G-lance] [G-fts] [A-context-spec]

## 6. Separate Trace Data comparison clones (2026-09-30)

The operator-approved local alternatives live **beside** Ariadne as sibling directories `ariadne-trace-data-dosi/` and `ariadne-trace-data-ktx/`; their READMEs are **local-only**, not GitHub links or part of this repository. KTX 0.16.0 creates and requires its own Git repository, so embedding it as an ordinary tracked Ariadne example would produce an accidental gitlink. Neither clone changes Ariadne's served example. Both carry the four approved S3 source declarations, a local glossary reference, unchanged original served artifacts for provenance, three active metric/policy reference pages, and two vendor-native single-source models with no raw many-to-many join. Metric pages point to clone-local models and the original owner-approved definitions; neither vendor structurally attaches those pages to numeric answers or enforces Ariadne's human Promotion gate.

Using DuckDB 1.5.6, Dosi 0.1.12 and KTX 0.16.0, an offline fixture compiled and executed all six vendor SQL variants with results **3 / 2 / 0.5**. A CA-verified local DuckDB runner then executed vendor-compiled SQL over the live, remote S3-backed views (not native KTX/Datus execution). On **2026-09-30**, Dosi and KTX both returned **1,045,861** EOL motors, **1,127,579** traced motors, and **1.0** trace coverage; Ariadne's live `get-metric eol_motor_volume` also returned **1,045,861**. The previous day's EOL value was **1,045,772**, so these all-time totals are a moving source snapshot, not a fixed golden oracle. Vendor model source SQL is AST-equivalent to the original, and the Dosi model files are byte-identical. KTX semantic YAML validation and metric wiki search passed; the Git-source Datus configuration and embedded Dosi catalog discovered three metrics. A full conversational Datus run lacked an LLM key; native KTX execution failed this private endpoint's TLS chain because its connector does not expose `ca_cert_file`. We did not disable TLS or store credentials. The clone READMEs give reproducible commands and precise caveats.
