## Owner requirement

In this conversation the owner clarified: “ariadne soll IMMER lumio-wiki nutzen. ABER lumio-wiki soll auch ohne ariadne existieren können.” The stated motivation is avoiding duplicate implementation of Context Layer creation and management. This supersedes the optional-dependency direction, not the human admission or source-access requirements. OptMem #507 records the clarification; this note records the supporting code inspection, not a replacement ADR.

**Subsequent owner constraint (same conversation): no backward compatibility is required.** The target does not retain a legacy runtime path, compatibility mode or compatibility-only CLI adapter. Earlier migration/adapter suggestions below are inspection-time alternatives, not requirements. Dropping compatibility does not authorize deleting existing data. In the subsequent structured clarification the owner selected:

- **Fresh setup, no migrator:** leave existing project data untouched; re-onboard needed sources/content deliberately and update repository examples to the new model.
- **Keep Answer Examples through Lumio:** explicitly saved questions/methods and their analytical provenance remain supported as knowledge, never as a current-answer cache or admitted metric.
- **Ordinary Lumio pages for operational guides:** no special Ariadne Skill profile; installed agent skills are a separate concern.
- **Structurally valid page batches:** persistent knowledge edits must satisfy the structural/cross-page contract as a batch. Business uncertainty and unreviewed drafts remain possible; structural validity grants no admission.

The owner then approved the complete in-chat target, including refusal before SQL when required Context is missing, with “Zielbild freigeben (Recommended)”. [Shared ADR-0029](../adr/0029-lumio-owned-context-layer.md) records the architectural decision; [spec0035](../specs/2026-11-09-0035-lumio-owned-context-layer.md) initially captured written revision 1. The 2026-11-10 follow-up below records the owner's targeted amendment request and current written revision 2. Earlier migration/compatibility suggestions below are historical inspection findings, not the chosen scope. No implementation is authorized.

The target dependency is `ariadne-data -> lumio-wiki`, never the reverse. A mandatory library does not require the private Lumio application, a server, S3, LanceDB, MCP, or an LLM provider. Ariadne still owns OSI/ODCS, physical source access, measurements, calculation and join governance. Lumio owns the knowledge-page lifecycle; technical facts supplied by Ariadne can live on those same pages.

## Migration risks and bounded verification targets

- Existing `context_layer/` content cannot simply be renamed. Frontmatter, Entity IDs, citations, Policy references, generated technical metadata and knowledge control metadata have different contracts. Preserve human-authored meaning and evidence; refuse unsupported conversion instead of dropping it. No generic OKF round-trip is presumed lossless.
- Existing approvals cannot be copied onto different artifact bytes. A migrated candidate needs the applicable validation and human admission. Prior admitted snapshots should not be rewritten.
- Mandatory Lumio storage alone does not decide a universal new Policy refusal rule. Preserve existing safety requirements while explicitly specifying any change to formerly advisory behavior.
- `context.py` contains legitimate Ariadne-specific evidence and mapping logic as well as legacy bundle management. Deleting the whole module would remove required functionality; retire responsibilities, not filenames.

Reuse the existing native-profile/navigation/release scenarios in `integration/tests/lumio_local_context.py` and `lumio_metric_mvp.py`. Necessary changed-contract scenarios are: base Ariadne installation brings Lumio while Lumio alone does not bring Ariadne; a new data-only project creates/reads native knowledge without classic mirror pages; schema refresh preserves curated text; a migrated project retains meaning and Policy/evidence links and requires honest admission; retained example/Skill behavior does not disappear. These are proposed checks, not executed results or authorization for broad suites.

## Recommendation

The owner has accepted the one-way dependency and the breaking, fresh-setup-only design captured in ADR-0029/spec0035. Review the written specification before implementation planning. Reuse the existing native profile/SDK path; do not build a third context backend, compatibility adapters or a migrator. The current code findings above remain evidence of work to remove or retarget, not a delivery claim.

### Separate defects and recommendations not to import wholesale

- **Effective PostgreSQL identity:** the audit's environment-variable-name gap is still visible in Core `authoring_sources._resolved_entries` and `storage_bindings_from_identity`; workspace `_grant` consumes those digests. This is a source-authorization correctness issue, not something the Lumio dependency fixes. Track it separately, or explicitly include its narrow repair if claiming spec0035 AC3 for PostgreSQL. Changing a database destination under the same variable name must not be confused with harmless secret rotation; never persist secret DSNs in pages. No live database probe was performed.
- **Pre-approval XLSX conversion and profiling limits:** the audits flag concrete source-access/bounding questions. They require their own focused disposition against the approved data-onboarding contract; removing duplicate Context code neither fixes them nor permits weakening the existing importer safeguards.
- **Four approval clicks:** fewer clicks may improve the workflow, but merging Source Approval, caller grants and content admission is not implied by one knowledge lifecycle. Preserve distinct authority facts and exact candidate binding; a changed browser workflow needs its own approval.
- **One owner is not one artifact:** Lumio publication receipts and Ariadne Bound Releases serve different purposes. Duplicate generic page/candidate plumbing is a simplification target already covered by spec0035; deleting analytics admission, replay/staleness checks or recovery records is not.
- **Not defects under the selected target:** an agent acting as Distiller is compatible with provider-free Lumio; extraction need not automatically produce final business semantics. Optional LanceDB need not become mandatory. Package independence for Lumio, separate release families and optional transports remain deliberate. Original full-text search is expressly excluded by spec0034, not a missing feature to add here.
- **Separate platform backlog:** reviewer inbox/notifications, broader identity/offboarding UX, Pi Entra upload, token-isolation qualification, operator connection provisioning, monitoring, deployment packaging, rollback UI and general graph/catalog expansion are not automatically part of the Context refactor. Concrete existing defects should not be labelled fixed or dismissed, but this review grants no repairs or platform redesign.

The audits reinforce ADR-0029's single knowledge-owner direction; they do not require reversing it. Recommend a bounded spec0035 clarification covering first/next publication, knowledge-only authorization, usable scoped discovery, binary-source review and integrated recovery coordination. Preserve the existing exact-release and numerical safeguards. At that comparison checkpoint these recommendations remained for owner decision; no implementation plan, tracker changes, product code or tests were created.
