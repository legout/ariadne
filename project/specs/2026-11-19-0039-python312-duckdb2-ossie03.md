## 1. Goal

All four packages install and pass on CPython 3.12 to 3.14 with DuckDB 2. The semantic
layer reads and validates Ossie `0.3.0.dev0` documents. Every repository fixture,
example and existing project can be converted to the new format by one command. The
numerical results stay the same, except for documented Ossie arithmetic semantics.

## 2. Non-goals

- The CLI unification, single approval, preview queries, change tiers and ad-hoc SQL
  (sub-spec B).
- Automatic drafting and Ossie/dbt/auto-ontology imports (sub-spec C).
- The Ossie relational and wide-table query interfaces, and Ossie ontology documents.
- Supporting Ossie field→field, metric→metric (other than `AGG`) and dataset→dataset
  sources ("Strikt Ossie").
- Any backward-compatible reading of the `0.2.0.dev0` envelope after migration. The
  loader rejects it with a pointer to `ariadne migrate`.

## 3. Python and tooling

1. `ariadne-data`, `lumio-wiki`, `lumio-lancedb` and `lumio-workspace` declare
   `requires-python = ">=3.12"`.
2. Every ruff configuration targets `py312`. This prevents the formatter from
   re-introducing 3.14-only syntax. All sources parse under CPython 3.12.
3. The lockfile resolves for 3.12. Dependencies that lack 3.12 support block this
   sub-spec and are reported, not worked around.
4. CI:
   - The required jobs run in full on 3.12 and 3.14.
   - A 3.13 job installs the wheels and runs the Core and Lumio smoke selection
     (wheel install, Core walkthrough, Lumio installed-wheel checks).
   - The Docker image keeps 3.14.

## 4. DuckDB 2

1. `ariadne-data` depends on `duckdb>=2.0,<3`. The lock moves to 2.x.
2. Bounded reads use the 2.0 API: cursor `fetchone`/`fetchmany` or an equivalent bounded
   cursor read, never removed relation methods. Result caps, overflow indicators, byte
   checks and the deadline interrupt behave unchanged.
3. Every source type (`sqlite`, `duckdb`, `csv`/`json`/`parquet`, `delta`, `iceberg`,
   `ducklake`, `postgres`, S3 storage profiles) attaches read-only and answers the
   existing tests under 2.x.
4. The [lock_down probe](../research/2026-11-19-lockdown-spike.md) is repeated under 2.x:
   - the stage 1 and stage 2 source matrix;
   - the escape cases;
   - gap classes G1 to G7;
   - the `json_serialize_sql` node types used by the planned parse-tree guard.

   The result is appended to that research note. Any behavior that differs from 1.5.6
   becomes a requirement input for sub-spec B. It does not change sub-spec A.

## 5. Ossie 0.3 semantic format

### 5.1 Documents and layout

1. Each `semantic_layer/models/*.yaml` (or `.yml`) file is **one** Ossie
   `0.3.0.dev0` document, with the model at the root.
   - `version: 0.3.0.dev0`, `name` and a non-empty `datasets` are required.
   - A `semantic_model` key, any other `version`, or a document that fails the pinned
     schema is refused. The message names the file and points to `ariadne migrate`.
   - Several model documents per project remain allowed. Model names are unique per
     project.
2. The pinned `ossie-schema.json` (commit above) ships in the wheel next to the existing
   ODCS schema, with its Apache-2.0 notice. It is validated with the existing
   `jsonschema` dependency. No new runtime dependency is added.
3. `semantic_layer/graph.yml` stays an **Ariadne-specific, non-portable** file. It holds
   cross-model relationships and conformed dimensions, using the same keys that Ossie
   uses inside a model:
   - `name`, `from`, `to`, `from_columns`, `to_columns`;
   - an optional `cardinality: one_to_one`. The default is many-to-one.
   - `conformed_dimensions` is unchanged.

   Its column names are dataset **fields** (§5.3).

### 5.2 Ariadne extensions

Ariadne-only semantics live in `nonportable_extensions` entries with
`vendor_name: ARIADNE` and an object `data`. Unknown keys under `data` are refused. Other
vendors' entries are preserved and ignored. Supported keys:

| Location | `data` keys | Meaning |
|---|---|---|
| relationship | `cardinality: one_to_one` | the edge is one-to-one; without it the Ossie default many-to-one applies |
| model | `conformed_dimensions: [...]` | the existing conformed-dimension declarations (same shape as today) |
| metric | `fill`, `window` | the existing output fill rule and post-aggregate window (same shapes as today) |

The `requires` gate and the DATUS `custom_extensions` hint are removed. Any Ariadne key
outside an `ARIADNE` extension is a schema error.

### 5.3 Name resolution (strict Ossie)

1. A field `expression` references only columns of its dataset's `source`. A field that
   references another field is refused.
2. `primary_key`, `unique_keys`, relationship `from_columns`/`to_columns` and every
   dimension in a query name **fields**. The compiler maps them to field expressions.
3. **Dataset-scoped metrics** (`datasets[].metrics`):
   - Unqualified names are fields of that dataset.
   - `source.column` names a source column.
   - They are aggregates over that one dataset. Each one is a fact-branch measure owned
     by its dataset.
4. **Model-scoped metrics** (root `metrics`):
   - Reference `dataset.field` or `AGG(dataset.metric)`.
   - A model-scoped metric composed **only** of `AGG(dataset.metric)` terms and
     arithmetic is a derived metric. It is evaluated after the fact branches align;
     this replaces today's recursive derived metrics.
   - A model-scoped aggregate over fields of **one** dataset is that dataset's
     fact-branch measure.
   - A model-scoped aggregate over fields of **more than one** dataset is refused in this
     revision. The message tells the author to declare dataset-scoped metrics and combine
     them with `AGG`. This keeps the existing fan-out guarantee without new join
     semantics.
5. Metric→metric references other than `AGG(dataset.metric)` are refused. Field and
   metric names within a dataset share one namespace.

### 5.4 Expressions and arithmetic

1. `expression.sql` (`OSSIE_SQL_2026`) is authoritative. When only `dialects` is present,
   the `OSSIE_SQL_2026` entry is used. Any other dialect alone is refused, because it is
   opaque to Ariadne.
2. Expressions compile through the existing sqlglot compiler to DuckDB SQL.
   - `/` is true division.
   - `ROUND(x, d)` rounds half away from zero. Where DuckDB's behavior differs for a
     type, the compiler emits an equivalent expression.
   - One golden test each pins `5 / 2 = 2.5` and `ROUND(-2.5) = -3` on a governed
     metric.
3. `datatype`, `description`, `label` and `ai_context` are preserved.
   - `ai_context` is guidance only. It is returned with context but never affects SQL,
     joins or Policies.
   - Ariadne does not enforce the `datatype` checks that Ossie leaves unspecified.

## 6. Metric identities

1. A **model-scoped** metric's identity is `<model>::<metric>`. A **dataset-scoped**
   metric's identity is `<model>::<dataset>.<metric>`.
2. These identities are used everywhere a metric is named:
   - query requests;
   - Policy Bindings (`subject.identity`);
   - Lumio `metric_ref` (`model` plus a `metric` that may contain `dataset.`);
   - Answer Examples;
   - Computation pages;
   - discovery and status output.
3. Lumio's `metric_ref` keeps `{model, metric}` and accepts the dotted metric. A Lumio
   SDK change is needed only if its validation rejects a dot. Lumio ADR-0030 is amended
   by note.
4. Query requests may use the short name when it is unique across the project. An
   ambiguous short name is refused, and the message lists the full identities.

## 7. Migration: `ariadne migrate`

> **§7.1 superseded by [spec 0040](2026-11-22-0040-one-cli-simple-governance.md) (B1):** `migrate` no longer opens its own proposal; it writes into the active draft.

1. `ariadne migrate --project P` rewrites a project from the `0.2.0.dev0` envelope to
   §5/§6. It follows the existing Git-managed route: it opens an Authoring Proposal with
   the rewritten artifacts, and the operator admits that proposal as usual. It never
   edits an admitted snapshot in place.
2. Rewrites:
   - Each `semantic_model` entry becomes one root document. A file holding several
     models is split; a single-model file keeps its name.
   - `ANSI_SQL` dialect expressions become `sql`.
   - `custom_extensions` are dropped. A DATUS hint is reported; any other entry
     becomes `nonportable_extensions` with its original vendor.
   - `requires` is dropped. `conformed_dimensions`, `fill`, `window` and relationship
     `one_to_one` move into `ARIADNE` extensions.
   - Keys and relationship columns that name source columns become the field that
     exposes that column. Where no field exists, a field named after the column is
     added.
   - Field→field chains are expanded to source-column expressions.
   - Metrics with an owning dataset become dataset-scoped. Derived metrics become
     model-scoped `AGG(dataset.metric)` compositions.
   - Policy Bindings, Lumio metric pages (`metric_ref`), Computation pages and Answer
     Examples get the new identities.
3. A construct that cannot be converted mechanically is reported per file with the
   reason, and the project is left unchanged. An example is a derived metric over a
   multi-dataset raw aggregate.
4. Re-running `migrate` on a migrated project is a no-op that reports "already Ossie
   0.3".
5. The same conversion, run from the repository, migrates every tracked fixture,
   example and test model. Tests that construct envelopes in code are updated to the new
   shape.

## 8. Acceptance examples

1. **Python:** on CPython 3.12, building the four wheels, a fresh install and the
   installed-wheel walkthrough all pass. The full required suites pass on 3.12 and 3.14;
   the 3.13 smoke passes. `ruff format` on a file that contains `except (A, B):` leaves
   the parentheses in place.
2. **DuckDB:** the lock pins DuckDB 2.x. Bounded result tests (caps, overflow, byte
   checks, deadline interrupt) and every source-type test pass. The lock_down probe
   results under 2.x are recorded.
3. **Ossie loader:** a migrated `retail_sales` model validates against the pinned schema
   and answers `revenue` = **150 EUR** and `completed_orders` = **2**. These are the
   values of the [historical joint example](../../integration/docs/tutorials/lumio-ariadne-local.md).
   A file that still contains `semantic_model:` is refused, and the message names
   `ariadne migrate`.
4. **Name resolution:**
   - `primary_key: [o_orderkey]`, where `o_orderkey` is a source column without a field,
     is refused.
   - A dataset-scoped `SUM(source.quantity)` compiles.
   - A field defined as `other_field * 2` is refused.
   - A model-scoped `SUM(orders.amount) / COUNT(DISTINCT customers.id)` is refused, and
     the message points to dataset-scoped metrics and `AGG`.
   - `AGG(orders.revenue) / AGG(customers.customer_count)` answers like today's
     equivalent derived metric.
5. **Arithmetic:** a governed metric `SUM(a) / SUM(b)` over integer columns returns a
   fractional value (`2.5` for 5/2). `ROUND(-2.5)` returns `-3`.
6. **Extensions:**
   - A relationship carrying `ARIADNE {cardinality: one_to_one}` keeps the existing
     one-to-one planner behavior.
   - An unknown `ARIADNE` key is refused.
   - A `DBT` vendor entry is preserved and ignored.
7. **Identities:**
   - `get_metric("sales::orders.revenue")` works.
   - `revenue` alone works when unique and is refused, with candidates, when ambiguous.
   - Policy Bindings and Lumio metric pages under the new identity pass admission.
   - Required-Context refusal before SQL still holds.
8. **Migration:**
   - `ariadne migrate` on the integration example produces a proposal whose admitted
     result passes AC3.
   - A second run reports "already Ossie 0.3".
   - A project containing an unconvertible construct is left unchanged, with a per-file
     report.
9. **Invariants:**
   - The existing numerical goldens, multi-fact alignment, grain/fan-out refusal, source
     containment, read-only execution, execution attestation and Policy closure tests
     pass after the fixture migration.
   - Expected values come from those tests' independent oracles and are not regenerated
     from the new implementation.

    (`ariadne_context.py`), so dotted metric names need no SDK change.
    Confirmed by reading the code.
