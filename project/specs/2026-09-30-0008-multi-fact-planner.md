## Purpose and boundary

A governed request may combine measures native to different fact datasets without joining raw fact rows or multiplying an aggregate. Shape and verify the generic feature now against synthetic facts; do not invent a relationship between Trace Data's EOL keys and product serials or wait for a production use case before defining the contract. Keep Ariadne's own sqlglot compiler, DuckDB execution session, no-unvalidated-execution invariant, source registry, Context Layer citations, and distinction between validated, human-reviewed, and independently value-attested results.

This specification covers the **query-planner breadth** of the compared KTX/Dosi approaches: typed multi-hop dimension paths, conformed dimensions, fact-local aggregation, multiple named measures, derived calculations, scoped filters/segments, aligned time/grains, parameterized metrics, window calculations, safe detail queries, ordering/limits, and inspectable plans/errors. It does **not** import KTX or Datus agents/knowledge stores, use the Dosi binary, implement Dosi change-attribution as a separate product, promise complete DATUS vendor-extension v1.9 compatibility, add new warehouse connectors, or provide native execution on non-DuckDB dialects. A future extension key is never silently assumed to work merely because the YAML parses.

## Authoring contract and normalized graph

1. **Domain layout:** an OSI `semantic_model` entry may contain several datasets, relationships and metrics in one business-domain YAML under `semantic_layer/models/`. **Source layout:** existing single-dataset OSI files remain valid; an optional `semantic_layer/graph.yml` supplies relationships and conformed-dimension mappings between models. The source layout is one OSI file per source, **not** KTX YAML imported as a second format. Both layouts feed the same normalized graph and the same validator/planner. Existing files need no migration.
2. Each dataset declares exactly one row grain through its key. One model may contain multiple datasets at different grains. A metric has exactly one owning fact for each base aggregate: resolve qualified columns to their dataset, and require an explicit dataset owner for an otherwise ambiguous `COUNT(*)`. Names/IDs must resolve unambiguously across the served project; duplicate metrics or conflicting graph declarations fail rather than overwrite or take precedence.
3. A typed `many_to_one`/`one_to_one` relationship permits a fact to obtain dimensions through a unique target; a `one_to_many` traversal may not relocate a duplicate-sensitive measure onto multiplied rows. Paths are bounded, acyclic, and unambiguous. A **conformed dimension** declares equivalent business group keys on multiple facts: it is never a physical fact-to-fact join. Its members must have compatible value types and time roles; one dataset cannot supply two members of the same class. No equivalence is inferred from identical column names or matching sample values.
4. Inline OSI relationships and an explicit conformed mapping (using a versioned, required extension where OSI core cannot express it) normalize to the same edge kinds as cross-file entries in `graph.yml`. Unsupported required extension keys, duplicate edges, and contradictory cardinalities are errors. The validator checks actual unique target keys and dataset grain where a source is available; an agent's declaration or a sampled match is not proof of cardinality. Existing pre-joined source SQL remains subject to `check_grain_preserving` and may be rejected.
5. Named derived metrics may reference base metrics across facts **only after** their branches aggregate and align. Reject dependency cycles, mixed-grain bare fields, and undeclared alignment. Keep business interpretation and policy citations in OKF, not in the relationship graph.

## Query and result contract

Add a transport-neutral `query_metrics` operation (local CLI and optional MCP adapter share the runtime) accepting a nonempty list of **predefined** metric names, declared dimensions, optional typed parameters, named segments, row/result filters, a half-open time range and time grain, order and limit. A separate detail operation fixes one declared root dataset and projects its fields through safe many-to-one paths without aggregates or fan-out. Neither accepts agent-authored `FROM`/`JOIN`/CTE SQL. The existing `get_metric` response and the existing single-dataset `define_metric` ad-hoc route remain compatible; there is no multi-fact ad-hoc route in this revision.

For metric queries:

- Resolve every requested metric and dimension to a declared dataset/field. A metric can be queried alone or with other metrics without changing its definition. Unreachable, ambiguous or unconformed dimensions fail with candidates/retry guidance. A grouping or row filter applying to several facts must resolve safely in **every** affected branch; never silently filter just one fact. Named segments expand to validated row predicates. A filter on a selected aggregate applies after aggregation; a context/population filter applies before windows. Unsupported mixtures have explicit errors.
- Aggregate duplicate-sensitive measures at their home dataset. Follow only safe many-to-one dimension paths inside a branch. Make a branch per required fact/axis, grouping and filtering on that fact's local conformed fields. Merge **aggregate outputs** on null-safe common keys; never join two raw fact row sets. The key union preserves groups occurring in only one branch and coalesces corresponding NULL-key groups once. With no dimensions, return one aggregate row. A bare COUNT missing from a group present only in another branch reads 0; other missing measures remain NULL. An explicitly declared fill rule may change a metric's output, never a denominator embedded in a ratio. Division by a zero or missing denominator yields NULL.
- A conformed primary time dimension permits each fact to apply the same half-open `[start, end)` range to its own business time and group at the requested `day/week/month/quarter/year` grain. Reject a requested grain finer than a declared native grain and incompatible time encodings; no implicit calendar spine or invented missing dates. Derived arithmetic/ratios and rolling, cumulative, prior-period, ranking and value windows operate at their declared post-aggregate stage. Window lookback must include the necessary preceding groups before trimming to the requested display range. Query parameters have declared types/bounds and are bound or lowered through the compiler AST, never concatenated into SQL.
- Return dimensions, metric columns, rows, compiled single-SELECT SQL, a bounded explain/lineage plan naming fact branches, joins, conformed keys, filters and window stages, and **per-metric** served OKF metric pages with their cited Policy bodies. Also return the admission route/revision, digest-bound validation scope, `governed: true` only for admitted definitions, and independent computation-attestation state. A missing/broken cited page fails validation for a newly admitted multi-fact definition; it cannot silently become an uncited governed multi-fact answer. Merely passing validation never means independent numeric attestation.

Compilation uses sqlglot ASTs and the existing read-only DuckDB connection. The runtime checks one statement, binder validity, and relevant grain/cardinality evidence before execution. For mutable sources without a verifiable immutable snapshot identity, recheck the participating relationship keys for each multi-fact request; a stale admission-time data scan alone does not prove today's rows. This may be expensive, but a performance optimization cannot exchange correct results for a silent fan-out.

## Validation, admission, and labels

One deterministic validator consumes either authoring layout and reports separate outcomes for (a) schema/graph/extension and metric dependency checks, (b) SQL compile and bind on the configured source registry, and (c) exact dataset-grain and relationship-target audits. It emits a **digest-bound validation report** with the consumed model/graph/cited-context digest, source-registry digest, validator version, checks performed, and errors. CLI output and Git CI display its scope as a label; no editable `validated: true` in a model is authority. A compile-only report is visibly partial, not a full pass. Business review and independent expected-value attestation are separate fields and actions.

- **Dev/test:** the human uses the existing Staging → Promotion process against the exact validated proposal digest. The promoter refuses changed bytes, failed/partial required checks, or changed approved source identity; it does not trust a free-form YAML label.
- **Production:** a human-reviewed Git change (for example an approved PR to the deployment branch) and a passing full validation check bound to the **same commit and artifact digest** are both required before that revision becomes the served deployment artifact. A commit alone or an unreviewed validated commit is not admission; runtime Git-status probing is not an approval mechanism. The deployment packages the reviewed/validated revision, not a mutable working tree. Production does not call the local Promotion CLI. Both admission routes load the same artifact format and runtime.
- An agent-generated Datus-style model may be proposed and validated, but does not enter the governed catalog until one of those human-reviewed routes admits it. Validation labels describe technical checks only. Existing ad-hoc single-dataset answers remain `governed: false` and proposals remain staged.

## Failure and compatibility behavior

Unsupported or unknown required extension semantics, ambiguous metric ownership/path, disconnected graph, unsafe fan-out, missing or incompatible conformed key, unsupported predicate position, invalid parameter/window, stale digest, unavailable required live audit, and nonunique declared join target all produce a structured error **before the compiled SELECT executes**. Error codes and candidate/retry information are stable API fields; message prose is not. Do not silently choose a path, drop a fact/filter, or downgrade to raw SQL. Existing single-dataset models, calls, golden values, and policy attachment retain their behavior; the new graph and multi-measure interface are opt-in. Model loading must reject duplicate metric names instead of the old last-file-wins behavior for the new admitted graph.

## Observable acceptance examples

1. On the existing synthetic orders/lines trap, define `orders_total` at order grain and `lines_total` at line grain, with line→order as a verified many-to-one dimension path. `query_metrics([orders_total, lines_total], [region])` returns NA **300 / 300** and EMEA **400 / 400**; a raw orders⋈lines aggregation would give NA orders **700** and is never emitted. The old pre-joined trap source still fails its grain guard. Both authoring layouts produce the same values and equivalent normalized plans.
2. Add a fact with an otherwise unmatched `APAC` group and one NULL group. Each appears once after the aggregate merge. A missing bare count reads 0, a missing SUM reads NULL, and a derived numerator/denominator with zero or absent denominator reads NULL. A cross-fact measure with an unpaired group/filter dimension fails explicitly; it does not broadcast an all-time total.
3. A two-hop many-to-one dimension path works when unique; duplicate target keys, an ambiguous alternate path, a `one_to_many` path that would move a SUM, an unsupported required extension, and contradictory inline versus cross-file mappings each fail before result execution. A changed source with newly nonunique target keys invalidates the next multi-fact request.
4. Pair differently named business-date fields explicitly. Monthly grouping and the same half-open range filter both branches correctly; a request finer than a declared native month fails. A rolling/prior-period metric scans its declared lookback then trims display rows. A typed parameter and segment change only the applicable fact population; an unpaired filter fails instead of affecting one side silently.
5. A validated cross-fact ratio may reference the two aggregated metrics; cyclic derived references fail. `explain` identifies both source branches and their conformed keys. A safe detail projection retains its chosen root grain; requesting a child relation that would multiply it fails.
6. Changing one model, mapping, cited Policy or source registry after validation invalidates the label/digest. Dev/test Promotion refuses that proposal until revalidation. Production rejects an unreviewed commit even with a passing report, and rejects a reviewed commit with a stale/partial report; the reviewed, fully validated commit serves with its admission and attestation fields distinguished.
7. Existing `get_metric`, single-dataset ad-hoc, source-registry, context, and fan-out tests remain valid without rewriting their artifacts. New tests use independent fixture SQL/values rather than treating the planner's own output as its oracle.
