## Purpose and boundary

A user chooses a role and converses with an Ariadne-owned Python agent, rather than operating Tau's coding application or relying on an outside agent to follow Ariadne's packaged skill. The agent interprets questions and selects allowed tools; Ariadne still owns every measurement, compile, grain check, execution, source-access decision, staging transition, and human Promotion gate. A validated result is not proof of business truth, and `governed: true` means Promoted, not independently value-attested.

The existing root distribution is renamed from `ariadne` to `ariadne-core` before the agent is packaged. Its Python import namespace stays `ariadne.*`, its existing CLI entry-point names stay unchanged, and its DuckDB query/compiler/grain path remains in the core; no `ariadne-query` distribution or second engine is part of this revision. The Agent is a **separately installable Python distribution** in `ariadne-agent/` within the same repository. Its dependency metadata names `ariadne-core` (not the unrelated PyPI `ariadne` GraphQL distribution) and Tau; installing `ariadne-core` alone must not import or install the new agent. The package uses `tau_ai` for an OpenAI-compatible model and `tau_agent.AgentHarness` for the conversation loop and asynchronous events. It must not import or invoke `tau_coding` at runtime, although the upstream `tau-ai` distribution still installs `tau_coding` and its dependencies. Pin the Tau version actually verified by implementation, not an assumed compatible range. The published [Tau v0.4.6 release](https://github.com/huggingface/tau/releases/tag/v0.4.6) is the next compatibility target; the existing local Tau/tau-mcp pair is v0.4.4. A v0.4.4 smoke does not establish v0.4.6 compatibility.

The approved `legout/tau-mcp` stdio client is reused through its embeddable-core contract (`legout/tau-mcp:project/specs/2026-09-29-0002-embeddable-mcp-core.md`), not copied into Ariadne. Ariadne's existing local CLI and optional MCP server remain independent and unchanged. The agent calls native Ariadne Python operations when local; MCP is for explicitly configured external stdio tools, not a mandatory hop back into a local Ariadne process.

Non-goals: a UI or `ariadne-ui` package, `ariadne-query` or other query engines, moving the root source tree, HTTP agent service, remote MCP/HTTP transport, built-in coding/file-write/shell tools, model-driven role routing, automatic role switching, durable conversation storage, a BI role without BI tools, autonomous source approval or Promotion, arbitrary user-installed skills or script execution, and a second compiler or MCP protocol implementation.

## Session and role interface

The public Python interface opens a session for one configured project, selected role (`analyst` or `authoring`), and OpenAI-compatible model; sends a user message and yields typed events asynchronously; permits cancellation and closes its resources. One session holds its own transcript and at most one active run. The chosen role and project cannot change inside a session. A caller that wants another role starts a new session, without silently transferring the prior conversation or its tool access. Messages are in memory: process restart loses them, and callers must be told this rather than offered a nonworking resume operation. The event stream exposes assistant text, tool activity, failures, and completion to Python callers; a later UI adapter can translate it into its own transport without requiring Tau's TUI.

The operator supplies model identity, endpoint and credentials outside user messages and data-project artifacts. The backend does not load Tau's personal provider configuration or global MCP settings implicitly. A model endpoint must support streaming tool calls in the configuration actually used; a failed model or tool call returns an error, not a switch to an unapproved provider or raw SQL.

Tool sets are constructed for the selected role, not merely described in prompts. **Analyst** gets Ariadne's query operations (`list_metrics`, `search_context`, `get_metric`, `list_datasets`, `define_metric`) and only explicitly approved external MCP tools. **Authoring** gets the harness-led source-proposal, measured-input, document-upload where supported, bundle-submit and bundle-review operations and only explicitly approved external MCP tools. Neither role gets `approve_sources`, `ariadne-promote`, arbitrary SQL execution, filesystem writes, or shell commands. Existing authoring digests, attempt limits, source approval and Promotion rules are not reimplemented in the agent.

Skills are curated instructions, not executable permissions. Load the version-matched packaged Ariadne `SKILL.md` and the bounded references needed for the role (notably `grain-rubric.md` for authoring); an operator may explicitly add trusted skill roots for that role. Skill discovery/read may return only approved `SKILL.md` content and references inside those roots. No automatic scan of the user's global agent directories or model-invocable skill script execution. The BI Agent role and its skills/tools will get a separate behavioral source when those capabilities exist; no placeholder BI tool is exposed now.

For MCP, the operator supplies explicit server configuration, cache location, and a per-role allowlist of qualified tool names. Existing `tau-mcp` proxy discovery and selected direct tools may be offered, but both discovery **and dispatch** must honor the role's allowed servers/tools. Hiding a direct tool while leaving it callable through the proxy is not authorization. A model request cannot alter the server commands, project root, allowlist, or model credentials. Ariadne source approval and Promotion are never registered for either role. An external MCP server's tool name cannot prove its effects: the operator must not allow tools that give the role a bypass around Ariadne's query or human-review gates.

## Role flows

**Analyst:** discover promoted metrics before selecting a route; search served Context Layer guidance for a novel business question; use `get_metric` when a governed metric answers it. Report returned values with the actual metric/Policy paths and caveats, including pending independent attestation when present. If no metric fits, inspect registered datasets and send a definition through `define_metric`'s compile/grain/read-only gate. Report `governed: false` and the proposal's staged status; never claim that a Context Layer page alone makes an ad-hoc calculation governed. A missing promoted catalog is an actionable Analyst error, not a reason to bypass the gate.

**Authoring:** work before first Promotion. Propose inert source entries, then stop until the operator approves the exact proposed digest outside the agent. Read the measured profile and approved document evidence in bounded parts; ask the owner or mark uncertainty where evidence does not establish a business rule. Submit Seed Notes, OSI and OKF through existing harness-led validation; repair the same proposal only with its current digest and within the established attempt limit. Review the exact staged digest, report it and stop for human Promotion. An unavailable source, failed check, stale digest, interrupted transition or `review_needed` state cannot be cleared or overridden by the agent.

## Failures, compatibility and verification

Cancellation ends subsequent model turns and closes session-owned MCP children on shutdown. A call already executing may finish or time out under the MCP client's bounded timeout; do not claim immediate interruption until cooperative call cancellation is demonstrated. One MCP server's failure must not make an unauthorized fallback tool available. Concurrent conversations must not share mutable role allowlists; existing authoring staging locks/digest checks own competing submissions.

Acceptance examples:

1. An Analyst answers the retail-demo governed and unmodeled questions through the actual Ariadne operations; the governed answer conveys the returned Policy caveats and citations, while the ad-hoc answer is labeled ungoverned and remains staged. Existing independent golden values remain the numeric oracle.
2. In an empty project, Authoring obtains inputs only after operator source approval, submits a reviewable bundle, reports the exact digest and stops. There is no path through its native or MCP tools to approve a source or Promote. Analyst's missing-catalog error does not prevent the Authoring session from opening.
3. When an MCP server offers both query and authoring tools, an Analyst sees only approved tools and cannot call an authoring-only tool via either a direct registration **or** the proxy; the server receives no forbidden call.
4. A permitted stdio tool is discovered and called with its actual schema, and session shutdown reaps its server. A server timeout or crash reports a bounded tool error and does not expand tool access. The existing Tau extension continues to work after core extraction.
5. Separate conversations retain their selected role and transcript only in memory; cancellation does not resume or duplicate a staged authoring submission. Importing/running `ariadne-agent` uses no `tau_coding` runtime modules. An installed `ariadne-core` wheel provides the same `ariadne.*` imports, CLI names and DuckDB-only CLI/MCP behavior; the Agent wheel depends on `ariadne-core`, never the unrelated GraphQL distribution.
6. Against the exact tested Tau release, a real tool-capable OpenAI-compatible endpoint produces streamed assistant/tool events for each role. If that provider is unavailable, deterministic checks are not called a passing live-agent smoke.

## Shaping capture checkpoint

- **Vocabulary:** `CONTEXT.md` names Ariadne Agent and Data Analyst Agent; existing Authoring Agent, Staging, Promotion and Governed/Ad-hoc Metric terms remain authoritative. `ariadne-core` is a distribution identifier, not a new domain term. The BI Agent is deferred.
- **Decisions:** ADR-0014 records the embedded Tau and separate-package boundary plus this owner-approved distribution-name amendment; ADR-0012 retains the optional MCP-extra decision. The owned MCP repository records its reusable-core choice in ADR-0002.
- **Behavior:** revision 2 changes only the package dependency and install naming, leaves DuckDB as the only engine, and retains revision 1's roles, Python interface, skill/MCP restrictions, failure behavior and acceptance examples. The owner approved documentation changes, not implementation, integration or publication.
- **Uncertainty:** verify the renamed root wheel and its optional-extra install without pulling the unrelated GraphQL package; independently confirm the embeddable Tau/tau-mcp interfaces against v0.4.6 and preserve the old extension install path. These are execution prerequisites, not permission to swap frameworks or transport.
