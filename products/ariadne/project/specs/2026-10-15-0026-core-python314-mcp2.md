## 1. Goal and non-goals

Move Ariadne Core to Python ≥3.14 and the same resolved official MCP SDK release as the committed Lumio Wiki integration baseline, without changing analytical behavior or admission authority. Retain the independent, local-first Core package and optional MCP transport.

Ariadne Agent, `tau-ai`, `tau-mcp`, the Agent lockfile, Agent documentation and Agent dependency declarations are explicitly deferred. Do not change their Python requirements, dependency sources, version pins or role contracts in this work. Existing Agent compatibility with the migrated Core is unverified until that later work; do not report an Agent install or the original complete #73 as passing.

Also excluded: Git-only authoring (#74), ODCS (#75), Context Provider/identifier/release-manifest design (#76), repository consolidation, data-project migration/admission, real company source access, model-provider calls and production configuration. No new MCP tools, permissions, compatibility framework or transport abstraction. No merge, push, issue publication/closure, release or deployment follows from this specification.

## 2. Runtime and dependency contract

- `ariadne-data` requires Python `>=3.14`. Supported acceptance runs use CPython 3.14 and record the exact patch version/platform. The change intentionally ends Core support for Python 3.12/3.13; it does not promise tested support for later interpreter releases.
- Core's optional `mcp` extra and development environment resolve **`mcp==2.2.0`**. The Core lockfile, installed MCP wheel checks and Docker/CI environment must agree. The SDK's own dependency on `mcp-types==2.2.0` must resolve normally, not be replaced with old 1.x types.
- The shared SDK baseline is `legout/lumio-wiki@93951f84f0dfe0c60f8e42ae3d607074a8c262cf`: its `uv.lock` resolves MCP 2.2.0 and its server uses `mcp.server.mcpserver.MCPServer`. Do not edit Lumio's metadata/lockfile or infer a shared domain interface from this SDK alignment. A later SDK upgrade requires coordinated acceptance, not a floating latest-version assumption.
- The base Core wheel remains usable without MCP, Lumio or Ariadne Agent installed. Imports and local CLI must not import the optional transport. The missing-extra error remains actionable; an internally broken SDK installation must not be mislabeled as an absent extra.
- Retain existing dependencies and their jobs; avoid unrelated resolver upgrades. If a required dependency cannot install or preserve its contract under 3.14, report the evidence and return the affected decision to the owner instead of widening/removing scope silently.
- Update the Core Docker runtime, CI interpreter selection, Ruff target and Core analysis environment paths consistently. Shared tooling may change only to make the Core target truthful; do not accidentally rewrite deferred Agent environments. A two-distribution release is not authorized or certified by a Core-only gate.

## 3. MCP adapter compatibility

Port the existing facade to `MCPServer` and its explicit Tool registration/types. Keep the transport change inside the adapter: no SDK imports in Query, Execution or shared business logic; no second compiler, query path or authoring workflow.

The Analyst, Authoring and Combined registrations preserve their existing tool names, JSON argument schemas, descriptions' behavioral promises, return payloads, human-only exclusions and project binding. In particular, the explicit nested `query_records` schema remains explicit. Existing CLI names and the `ariadne.serve.Facade` compatibility alias remain available.

Preserve governed/ungoverned labels, complete result metadata, SQL provenance, mandatory Policy/caveat/quality disclosure, grain/fan-out/SQLGlot/source containment checks, Source Approval and exact-revision Git Review Admission. No mutable-working-tree fallback or automatic admission is added. Existing legacy staging/Promotion and Answer Example behavior remains unchanged until separately approved #74 work.

MCP Python model names may change to the SDK 2.x API; public JSON uses the protocol aliases. Existing clients must still receive ordinary results and structured refusals/errors, not Python representations or SDK model objects serialized as strings. Do not enable an inferred output schema or text/structured duplication that changes an existing tool contract silently.

### Output and error bounds

The spec 0014 limits retain their values, complete-output requirement and request-ID reserve. A response is measured in the representation actually emitted by MCP 2.2.0, including escaping, aliases, text/structured content, error fields and JSON-RPC framing. Never retain a 1.30 serialization model just because a matching dict fits.

A fitting success returns the full existing payload. A success that would overflow the transport ceiling is a bounded tool-error refusal with the existing refusal body and `isError: true`, not partial success. Generic errors retain existing public semantics and are bounded too. Refusal handling must not recursively overflow or disguise an error as success.

For ad-hoc metric execution, complete Core and transport preflight still precede any staging write. An output refusal leaves no staged proposal; a fitting narrowed retry executes afresh. No automatic retry or exactly-once guarantee is introduced.

## 4. stdio and opt-in HTTP

stdio remains the default. Real SDK 2.2.0 clients can initialize, list tools and call representative tools for each registration. Preserve clean protocol stdout and bounded failures.

HTTP remains explicit opt-in with the same project/toolset surface and routes. Adapt SDK configuration through supported 2.2.0 parameters, not removed mutable settings. Preserve:

- loopback-only default binding and the explicit private-container `0.0.0.0` exception;
- server-environment bearer token, with missing-token startup refusal before listening;
- the outer ASGI bearer gate on every HTTP request, before session management or project reads/writes; missing/wrong tokens return the same fixed 401 body without leaking credentials or project data;
- SDK DNS-rebinding protection with explicit host/origin additions, never a disabled safeguard as a migration shortcut;
- the existing upload body allowance and tool-level 5 MiB bound, plus `healthz`/`readyz` behavior and session/lifespan cleanup.

Do not add OAuth, public ingress, unauthenticated probes, HTTP Agent transport or a new authorization layer. Verify clients over real loopback HTTP; no production network or deployment is needed.

## 5. Observable acceptance

1. **AC1 — Core installation:** build the Core wheel under CPython 3.14, install it into a clean environment and run local CLI/import smoke without MCP or Agent/Lumio packages. Install its MCP extra into another clean environment and assert the actual SDK/types versions are 2.2.0. Core metadata, lockfile and tooling agree; Agent files remain unchanged.
2. **AC2 — Real stdio contracts:** SDK 2.2.0 clients initialize/list/call Analyst, Authoring and Combined servers on synthetic temporary projects. Existing toolsets/schemas and human-only exclusions match. A fresh unadmitted project can author but cannot serve a governed answer; an admitted fixture returns the independently specified existing golden values and full caveats.
3. **AC3 — Actual framing:** compare real success, structured-refusal and generic-error JSON-RPC frames against preflight accounting, including Unicode/escaping and the supported request-ID reserve. Lowered ceilings exercise the near-boundary case where an inner dict fits but its envelope does not. Refusals are bounded and no failed ad-hoc output stages artifacts; a fitting retry succeeds without losing required content.
4. **AC4 — Real HTTP protection:** a loopback SDK 2.2.0 client initializes/lists/calls with the configured bearer. Missing/wrong bearer requests are denied before dispatch, including bootstrap and probe routes. Binding/token refusal, host/origin protection, upload bound and health/readiness behavior stay effective. All temporary listeners/processes close.
5. **AC5 — Core regression:** existing numerical/golden, grain/fan-out, SQL/source containment, deadline, admission and affected CLI/authoring checks pass on CPython 3.14. Use synthetic fixtures and the existing independently defined expectations, not values copied from the migrated implementation.
6. **AC6 — Docker:** build the Core image with Python 3.14 and exact MCP 2.2.0. In a disposable private test setup, verify actual interpreter/SDK versions, startup, bearer refusal and an authenticated MCP call; preserve the existing external-project/recreation contract. Do not restart or reconfigure existing services.
7. **AC7 — Cross-repository SDK alignment:** inspect the pinned Lumio lockfile and test the committed Lumio server with SDK 2.2.0 on a small temporary local KB fixture, without editing its active checkout. A bounded client initialization/list/read and failure check proves SDK compatibility only, not a Context Provider or release/admission manifest.
8. **AC8 — Honest delivery:** guidance names the new Core minimum, optional MCP pin and Agent deferral. Report exact candidate commit/tree, interpreter/SDK/dependency versions, commands/results and unavailable checks. Required missing capability is a blocker, not a skipped passing result. Do not close #73 while its original Agent scope remains deferred.

Reuse focused existing checks for preserved behavior. Add only focused tests for uncovered SDK2 framing/HTTP/installed-package failures. Existing capability-locked S3/Lakehouse obligations in spec 0025 remain in force; the existing publication-job exclusions are not blanket permission to claim full qualification. Missing extension/fixture capability must be reported for the affected claim, never hidden by relaxing checks.
