# OKF v0.3 and the current Ossie core spec: what changes for Ariadne and Lumio

Date: 2026-11-28. Status: research note (planning-contract: research; grants nothing).
Sources read in full:
- OKF `SPEC.md` v0.3 at `open-knowledge-format/open-knowledge-format@527e81a` (2026-11-18), and the Google Cloud blog "Introducing OKF v0.3".
- Apache Ossie `core-spec/spec.md` (`0.3.0.dev0`, still DRAFT) at `apache/ossie@4d70c2a` (2026-11-28), `docs/spec_changes.md`, `core-spec/ossie-schema.json`.
Checked against main `beb3357` and the lab project (`~/ariadne-lab`, synthetic data).

## 1. Ossie

### 1.1 Where we stand
- ADR-0028 / spec 0039: Ariadne reads Ossie `0.3.0.dev0`, one model per file, `expression.sql` authoritative, strict name resolution, schema vendored at a pinned commit (`schemas/ossie/ossie-schema.json`), Ariadne-only semantics under `nonportable_extensions` (`vendor_name: ARIADNE`), `graph.yml` kept as a non-portable file.
- The version string is unchanged upstream (`0.3.0.dev0`, "schema may change before 0.3.0 is released"; the next release is planned as `0.3.0-incubating`). No migration of documents is needed.

### 1.2 Upstream changes since our pin (measured)
The vendored schema differs from upstream HEAD in 10 lines:
1. `primary_key` and each `unique_keys` entry gain `"uniqueItems": true` (PR #705, 2026-11-13): a key names each field once.
2. The dataset-metrics description now allows `AGG(source.measure)` when the `source` is a measure relation (PR #726, 2026-11-20).
Spec-text changes without a schema effect:
3. `METRIC()` is reserved for metric definition in the relational layer (PR #774, 2026-11-26); `AGG()` is its counterpart.
4. `OSSIE_SQL_2026`: `ROUND(x, d)` breaks ties half away from zero and `/` is true division (PR #687, 2026-11-12).
5. Unquoted field names resolve case-insensitively (expression_language.md), so `[email, EMAIL]` is one field named twice.
6. New Layer 2 (Relational Query Interface, `MEASURE()`) and Layer 3 (Wide Table Query Interface) documents; additive, no new core field.
7. A `datatype` enum (`String … DateTimeTz, Opaque`) with the rule that `is_time` defaults to true for temporal datatypes.

### 1.3 Our behaviour today (probed with `ossie.parse_model` in the lab venv)
| Case | Upstream | Ariadne today |
|---|---|---|
| `primary_key: [id, id]` | invalid (uniqueItems) | ACCEPTED |
| `primary_key: [EMAIL]` with field `email` | valid (case-insensitive) | REFUSED ("not a declared field") |
| `primary_key: [email, EMAIL]` | invalid (one field twice) | refused, but for the wrong reason (case) |
| dataset metric `AGG(source.total_revenue)` | valid on a measure relation | REFUSED ("AGG is only valid in a model-scoped metric") |
| `/` on integers | true division | DuckDB 2.x: `5/2 = 2.5` (matches) |
| `ROUND` ties | half away from zero | DuckDB DECIMAL: `2.5→3, -2.5→-3` (matches); DOUBLE `2.675→2.67` is binary representation, not a tie rule |
| `datatype` temporal ⇒ `is_time` default | yes | implemented (`ossie.py:306`) |

### 1.4 Consequences
- **Must (small):** refresh the vendored schema to a new pinned commit and refuse a key that names a field twice (also by case), with the upstream wording. Standard lane; ADR-0028 gains the new pin.
- **Decide (owner):** case-insensitive identifier resolution. Upstream says unquoted names resolve case-insensitively; we compare exactly. A document that is valid upstream (`primary_key: [EMAIL]`) is refused by us, so "strict Ossie" (ADR-0028) is not met here. Adopting it touches every name lookup (fields, keys, relationships, `dataset.field`, `source.column`) and metric identities (`model::dataset.metric`); it is a behaviour change with a review of collisions. Recommendation: adopt, as its own deep issue, before more models exist.
- **Decide (owner):** `AGG(source.measure)`. It only makes sense when a dataset's `source` is a measure relation (a semantic view/another engine's measures). DuckDB sources have none today. Recommendation: keep refusing, but with a message that names the reason ("the source is not a measure relation"), and record in ADR-0028 that measure-relation sources are out of scope. No code beyond the message.
- **Watch:** Layer 2/3 query interfaces. Ariadne's `get_metric`/`query_metrics` is a Layer-3-like wide-table interface with its own request shape. Nothing forces a change; if the spec's Layer 3 stabilises, mapping our request to it is the portability step. No issue now.
- **Unchanged:** `nonportable_extensions`, one model per document, dataset-scoped metrics, `AGG(dataset.metric)`, `source.column`: all already implemented.

## 2. OKF v0.3

### 2.1 Where we stand
- Lumio is the Context authority (ADR-0029 shared, spec 0035). Pages are Lumio Compiled Pages with Lumio frontmatter (`id`, `entity_types`, `summary`, `lifecycle`, `visibility`, `sources`, `ariadne_profile`); they are NOT OKF documents (no `type`).
- OKF is an exchange boundary only: `lumio_wiki/okf.py` exports/imports "Profile 1" (OKF v0.1, pinned commit) and "Profile 2" (OKF v0.2, pin `3fcbb9f`). There is no v0.3 profile.
- Ariadne ADR-0007 still says the context layer "adopts the OKF v0.2 bundle structure"; ADR-0029/spec 0035 superseded the storage part, the wording was not updated.
- Ariadne's advisory trust view (`context.py::_verification_tier`, spec 0011) derives unverified / machine-confirmed / human-reviewed from `verified` entries.

### 2.2 What v0.3 changes (two breaking, the rest clarifications/additions)
1. **Path fields resolve from the file's directory** unless they start with `/` (was: bundle root). Fallback allowed for bundles declaring ≤0.2 or no version.
2. **Only current verification events count** for the trust tier: an event is current when `verified.at >= generated.at`. An agent rewrite after a human review drops the tier until a human confirms again.
3. A `.md` file without `type` is not a concept (README/AGENTS/SKILL may live in a bundle); non-`.md` files are assets; dot-paths are outside the bundle.
4. Bundle metadata in the root `index.md` frontmatter: `okf_version`, `title`, `description`, `license`; regenerating `index.md` must keep it.
5. `superseded_by` for deprecated concepts (forwarding address; also for moves/renames).
6. Extension keys allowed at every level; producers must preserve unknown keys; `x-<producer>-<name>` is reserved for producers forever.
7. Actor convention: `<producer>/<version>` or `<scheme>:<id>`; new `team:` scheme; only `human:` yields human-reviewed.
8. Links are untyped directed relationships; path fields that resolve to a concept are graph edges too (§6.4). `[[wikilinks]]` are not links. Typed relationships are explicitly deferred ("use links, path fields and extension keys").
9. Attested Computation: `parameters` need `name` and `type`; an attester verdict has at least `ok`; a value is never shown as attested without `runtime` and `attester`. The full receipt/verdict protocol and semantic-layer attestation are deferred.
10. Consumer tolerance rules (null = absent, single item = list, unknown status is not stable).
11. Ecosystem: "use cases" folder (OKF next to other standards) and two agent skills, `okf-generate` and `okf-consume`; the repo moved to `open-knowledge-format/open-knowledge-format`.

### 2.3 Consequences
- **Real defect in our own semantics (independent of the exchange):** `_verification_tier` returns `human-reviewed` as soon as ANY `human:` entry exists; it never compares `at` with `generated.at`. Under v0.3 (and by plain reasoning: an agent edit after the review is unreviewed) this over-states trust. Spec 0011 defines the tier; it needs the "current events only" rule. Standard lane with a reviewer (it changes a disclosed trust signal). Lumio's own trust model should be checked for the same rule in the same issue or a sibling.
- **Exchange Profile 3 (OKF v0.3) for `lumio_wiki/okf.py`:** new pin, `okf_version: "0.3"` plus bundle `title`/`description`/`license` in the root index, file-relative path fields (and the ≤0.2 fallback on import), `superseded_by` mapped to Lumio's page removal/rename/merge history where one exists, actor strings validated against the convention, Lumio extension keys moved to an `x-lumio-…` name (today a bare `lumio` extension key, which v0.3 no longer protects from a future collision), preserve unknown keys on import/export round trip. Deep lane (public file format), Lumio-owned.
- **Typed edges:** OKF defers typed relationships and tells producers to use links + path fields + extension keys. That is the same question as the lab finding "Ariadne pages form no Lumio graph" (issue #207): if Ariadne emits ordinary Markdown links (metric → reference/policy/table, computation → metric) in the body and Lumio reads them as edges, the pages are a graph for Lumio AND for any OKF consumer, without inventing a format. This should be the first option the spike evaluates.
- **Attested computations:** our generated Computation pages already carry `runtime` and `attestation: pending` and never claim attestation (ADR-0007 scoped extension). v0.3 confirms that stance ("MUST NOT show a value as attested without runtime and attester"). On export a Computation page can become `type: Attested Computation` only with a real `attester`; until then it must export as a plain concept or with the attestation fields omitted. Check this in Profile 3; no new product behaviour.
- **Skills:** `okf-generate`/`okf-consume` are generic. They do not replace the `ariadne` or `lumio-wiki` skills (ours carry the approval/admission rules). Worth one line in the Lumio skill: "an exported OKF bundle can be read with okf-consume".
- **Docs:** ADR-0007's sentence "adopts the OKF v0.2 bundle structure" should be marked as superseded for storage (ADR-0029) and point to the exchange profiles; one line, with the Profile 3 issue.
- **No change needed:** OKF does not ask us to store pages as OKF. Lumio stays the canonical model; OKF remains an optional, best-effort interchange.
