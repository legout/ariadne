# Multi-S3 credentials through DuckDB scoped secrets

As of: 2026-10-14. Evidence for the Multi-S3 design, not an approved behavioral contract or implementation authorization. Repository inspected at `a66a012` (Ariadne 0.3.0). Project artifact mapping takes precedence over a duplicate global-wiki capture.

## Question and owner scope

Use distinct S3-compatible endpoints and credential sets in Ariadne's shared DuckDB connection, with values supplied by process environment variables and credential-free references in the source registry. The owner selected unique S3 paths across endpoints, no automatic environment-file loading, and inclusion of the existing Delta, Iceberg and DuckLake source types as well as file/native DuckDB sources.

## Primary-source findings

1. DuckDB secrets select credentials by file-path prefix; the longest matching prefix wins. A view/source alias does not select the secret. Two different endpoints with the same scope therefore cannot be safely distinguished through the existing source alias alone. The bounded design can refuse intersecting scopes belonging to different named storages. Source: [Secrets Manager](https://duckdb.org/docs/current/configuration/secrets_manager.html).
2. S3 secrets support `KEY_ID`, `SECRET`, `SESSION_TOKEN`, `REGION`, `ENDPOINT`, `URL_STYLE` and `USE_SSL`. The `config` provider permits explicitly supplied values. This supports resolving named environment references in Ariadne, without enabling an AWS credential-provider search. An endpoint URL needs conversion to hostname/port plus its HTTP(S) transport setting. Source: [S3 API Support](https://duckdb.org/docs/current/core_extensions/httpfs/s3api.html).
3. DuckDB still documents the legacy mapping from `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` and region variables into S3 settings. A preceding local synthetic-value probe on DuckDB 1.5.6 confirmed this mapping after `LOAD httpfs`, with no bucket access and no real credentials. This is one global fallback, not named Multi-S3 support. DuckDB recommends secrets rather than exposing credentials in settings. Source: [Legacy Authentication](https://duckdb.org/docs/current/core_extensions/httpfs/s3api_legacy_authentication.html).
4. Delta documentation explicitly supports DuckDB S3 secrets and notes that some network operations use `delta-kernel-rs`/`object_store`, with credential-chain differences. Its implementation looks up a secret by the actual path and secret type, and reads `key_id`, `secret`, `session_token`, `region`, `endpoint`, `url_style` and `use_ssl` before building the Delta engine. Sources: [Delta extension](https://duckdb.org/docs/current/core_extensions/delta.html), [`delta_multi_file_list.cpp`, lines 179–276](https://github.com/duckdb/duckdb-delta/blob/e9cd304ad55ee08faa3dc546a1f16ac7e7cee3f9/src/functions/delta_scan/delta_multi_file_list.cpp#L179-L276). That upstream commit is evidence, not proof that every installed Delta extension has the same behavior.
5. File-based `iceberg_scan` uses `httpfs` for S3 object-store access. REST-catalog attachment and its catalog-authentication secret are a separate interface; they are not required to add named S3 credentials to Ariadne's existing file-based scan. Source: [Iceberg overview](https://duckdb.org/docs/current/core_extensions/iceberg/overview.html).
6. DuckLake separates its metadata connection from the data-file location. An existing lake loads `DATA_PATH` from metadata when not explicitly overridden. A local metadata database can therefore depend on remote S3 files even when the registry `path` itself is not an S3 URI. Sources: [DuckLake connecting](https://ducklake.select/docs/stable/duckdb/usage/connecting.html), [DuckLake paths](https://ducklake.select/docs/stable/duckdb/usage/paths.html).
7. DuckLake's upstream MinIO test configuration creates an S3 secret with an explicit endpoint, path-style URLs and HTTP, and sets `DATA_PATH` to an S3 bucket. This is direct upstream evidence for the combination, not a local Ariadne read test. Source: [`test/configs/minio.json`](https://github.com/duckdb/ducklake/blob/900cf2f983df3ed5cb1e019de61b4c1516b058d8/test/configs/minio.json).

## Repository implications

- `src/ariadne/sources.py`: `SOURCE_KEYS`, `Source`, `Registry`, `validate_entries`, `load_registry`, `plan` and `build_connection` form the shared source boundary. Current planning contains no named storage definition or secret setup. Public statement planning must not become a carrier for resolved credential literals.
- `src/ariadne/authoring_sources.py`: source proposals, declared identity, approval lookup and approved-registry reconstruction currently transfer only source entries. A new storage reference must not lose its definition during this transfer.
- `src/ariadne/authoring.py`: validation materializes an approved registry and caches evidence using the source digest; mapping receipts also bind that digest. Endpoint changes must invalidate applicable validation and measured evidence, not only connection setup.
- `src/ariadne/admission.py`: admission verifies complete recorded source identity and reconstructs the pinned runtime registry. Any effective storage binding must survive this path without consulting mutable candidate files or copying credentials.
- `src/ariadne/status.py`: proposal status derives source declarations without opening sources. Introducing named profiles must not make offline inspection require credential values.
- Legacy source proposal/approval, staged-bundle submission and Promotion also bind source declarations. Their storage definitions and runtime bindings need preservation rather than a managed-route-only implementation.
- `src/ariadne/serve.py`, `src/ariadne/authoring_cli.py` and `ariadne-agent/src/ariadne_agent/authoring.py` explicitly describe/pass typed source proposals. Optional storage definitions need adapter parity; source approval remains human-only.
- `compose.yaml` forwards only the HTTP MCP token by default. A Compose `.env` is not an automatic export of storage credentials into the container.

## Limits of this evidence

No Multi-S3 implementation, extension installation, product test, real S3 authentication, TLS/CA test, Lakehouse read, or deployment was performed in this design investigation. In particular, upstream Delta source and the DuckLake test configuration do not establish the installed runtime's complete compatibility. Implementation needs real loopback S3-compatible reads with independent fixtures for the claimed source types; statement-only checks cannot establish credential routing. Named profile configuration is not a backing-resource sandbox for trusted views or Lakehouse metadata, and credentials do not grant Source Approval or metric governance.
